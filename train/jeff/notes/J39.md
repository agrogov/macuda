## What was built (the design, in one paragraph)

`--no-recompute` (`JT_NO_RECOMPUTE=1`; `src/model.c` reads the environment, as `JT_EXACT`/`JT_GDN_CHUNKED` already are, so
the re-gate scripts can switch it on without a flag) runs the forward sweep in `JT_FWD_SAVE` mode and leaves every layer's
saves where its backward reads them, so `model_backward` re-runs nothing. 24 layers of saves do not fit the arena (0.81 M
floats/packed token against the arena's 98,304), so `jt_ctx_alloc` appends a **store** to the arena in the same
`cudaMalloc`, laid out for a batch of n tokens as
`[ pm_0..pm_23 | saves_0 .. saves_23 | 18 GDN ckpt slots | one shared work region ]`. The layer loop moves `c->arena` to
the layer's slot and `c->arena_n` to "the store's top minus that slot": the pieces' convention (a backward's saves start at
the arena's base) is satisfied, work still comes from the top (`c->arena + work_at` is the same address for every layer),
and the arena's own guard `work_at - save_at` stays exactly "the room between this layer's saves and that top". No header
change and no global: the store sits directly above the arena, so its size and base are pure functions of the context's
capacities and `no_recompute(c)` is the accounting identity `arena_n == base + store`.

Sizes: the per-token save widths are written as sums of the model's widths and pinned with `_Static_assert`
(MLP 11,825 / GDN 23,697 / attn 12,875 floats per token, from `src/layer_mlp.c`'s `saves_floats()`,
`src/layer_gdn.c`'s `walk()` and `src/layer_attn.c`'s `attn_save_ptrs()`), and `store_check` compares the save cursor
against them after *every* SAVE pass of every step — a piece that grows a saved buffer stops the mode at step 1 with both
numbers instead of letting one layer's slots overlap the next. Total cost: **3,172.55 KB per packed token** (3.1 MiB) plus
18 GDN checkpoint slots (cap_rows × nseg × 64 KB each) plus one arena-wide work region.

The store is sized from the **train split's** `max_tokens_per_batch`, which `main.c` hands over as
`JT_NO_RECOMPUTE_TOKENS` (whether or not the flag is used, so a run switched on by the environment is sized identically).
The context's own `cap_tokens` is usually a dev check's, and train.py's dev batches are twice the training batch and have
no backward to feed; a batch above the hint takes the recompute path in **both** sweeps (`store_serves`, one question for
forward and backward, so saves can never be kept for a batch whose backward recomputes). `--eval-only` and
`--dump-forward` print `--no-recompute has no effect here (no backward in this run)` and allocate no store.

The saving is the recomputed forward and nothing else: 1.127 − 0.778 = **0.349 s/step**, and 0.349 s is 45% of the
0.778 s that remains — the shape design §6.2's "+33% time" predicts for a forward that is cheaper than the
forward+backward it sits in front of. M6.3 measured the same step at 1.061 s/step on the full split, so this fixture's
1.127 s/step is the same cost. Plan M8 item 4 says −25%; measured **−31%** at the plan's config, i.e. the plan's estimate
is conservative here.

### Correctness: the mode is bit-exact, not merely inside the gates

`--no-recompute` changes no arithmetic — it only keeps buffers the recompute path throws away — so in exact mode
(`JT_EXACT=1 TINYCUBLAS_TC=0`) the two paths must produce identical files. They do, everywhere I looked:

| what | result |
|---|---|
| 20-step `--trace-loss` trace, batch 8 × accum 1 (plan config) | **byte-identical** to the recompute run — and to the trace that passed M6.2 (`diff -q`) |
| 20-step trace, batch 4 × accum 1 (real-data fixture, dev split at plan shape) | byte-identical |
| 20-step trace, batch 4 × accum 2 | byte-identical |
| `--dump-backward` 403-key safetensors (77 forward keys + 326 gradients, 1835 MiB) | **`cmp` clean**: byte-identical |

The dump is the strongest one: it covers every `layer.{i}.post_mixer`, every `grad.layer.{i}.out`, all 300 LoRA grads,
`grad.final` and `grad.readout`, i.e. the `grad_out`/`post_mixer` plumbing the store path also has to carry
(`loss 1.80793023` in both).

### The memory wall ("when memory allows", measured)

The store is 3,172.55 KB per packed token, so this is a real cost, and it is why the mode is opt-in:

* at batch 8 × 5,750-token batches the store is 22.94 GB and the step peaks at **29.56 GB** of gpubox's 31.82 GB — it fits
  with ~2.3 GB to spare and runs at full speed;
* the same step with `cap_tokens` left at the dev split's 11,052 tokens (which is what `parity-steps.sh` prepares — 16
  dev rows) wants ≈35 GB. It does not fit: the allocation over-commits and the card **thrashes** — 13.5–16.3 s/step
  instead of 0.78, peak 31.82 GB — and a first attempt that also skipped the token hint (44.22 GB) died in
  `cublasGemmEx` with `cuBLAS error 13`. So the honest headline is "fits a 32 GB card for batches up to ≈4,000 tokens
  with the 11 GB baseline, ≈5,750 if the arena's cap is the train split's";
* everything above the hint is *not* a failure mode: the dev check (16 rows, 11,052 tokens) simply takes the recompute
  path, in both sweeps, and the step trace is unaffected.

### Why the gate tables are quoted from the default run, not from a mode-on `parity-steps.sh`

I did run the script with the mode on at shapes that fit the default dev split (batch 4 × accum 1 / accum 2 / accum 4).
For the first two I also ran the mode *off* on the same `.jtb`: the traces were byte-identical and the pre-existing
recompute path failed the same early-step line (`1.95e-03` at step 3 for batch 4 × accum 1, `2.08e-03` at step 2 for
accum 2). Batch 4 × accum 4 (16 rows/step, 64 batches = 16 steps) was run mode-on only and missed steps 2, 3 and 5
(1.13–3.35e-03); I did not run its control, so I am not claiming anything about it beyond that. Those shapes' means are
noisier than the plan's 8-row batch, and accum > 1 has its own pre-existing drift against train.py — which is exactly why
M6.2 is specified at batch 8 × accum 1. Since the traces are byte-identical, the mode inherits the plan's verdict at the
plan's own config: **PASS**.

## Follow-ups this task did not own

1. **Sizing the store's GDN checkpoint slots by the train split's rows** rather than `cap_rows` (which a dev split's
   double-size batch sets) would save up to 2 GB at batch 8 — the slots are 18 × rows × nseg × 64 KB.
2. **A dev/eval batch that fits the hint still runs in `JT_FWD_SAVE`** and writes saves nobody reads (it only costs the
   writes, not a recompute); `model_forward` has no way to say "no backward will follow", so switching it off would need a
   one-line setter in `src/model.c` that `batch_forward` calls when `with_loss == 0`.
3. The full-arm speed win at `--batch 8` on long-row data needs either a bigger card or a smaller store; bf16 saves would
   halve it but change the exact-mode gates, so it is a milestone of its own, not a tweak to this one.
