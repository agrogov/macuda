## Why it is blocked

A bf16 GEMM in cuBLAS needs **both** operands bf16 (`Atype == Btype`; the shim enforces it in `cublas.c`'s
`gemm_contract`, real cuBLAS returns `CUBLAS_STATUS_NOT_SUPPORTED`). Since design §6.1 keeps activations fp32, item 1
therefore needs two things that are not in my file list:

1. **`kernels/misc.h` + `kernels/misc.cu`: `void jt_f32_to_bf16_n(const float *src, unsigned short *dst, size_t n, cudaStream_t s);`**
   (fp32 → bf16, round-to-nearest-even, i.e. `__float2bfloat16`). `kernels/` already has `jt_bf16_to_f32_n` (`misc.cu:79`)
   and no reverse; nothing else in the tree converts fp32 → bf16. Plan rule 2 also wants `ref/misc.c`'s
   `ref_f32_to_bf16_n` and a `test/k_misc.c` group check first, so this is one small task in whoever owns `kernels/misc.*`,
   `ref/misc.c` and `test/k_misc.c`, not a one-line addition. Without it the GEMM's activation operand cannot be produced.
2. **`src/linear.h`: a bf16 weight pointer** (e.g. `const unsigned short *Wb; /* [out][in] bf16, the checkpoint's own bits */`
   next to `W`), **and `src/model.h`: a bf16 arena** (`unsigned short *wb; size_t wb_el;`) so `model_load` can keep a
   `put_linear` weight as bf16 instead of widening it. `struct Linear` and `struct Model` are frozen interfaces
   (`linear.h` is plan J18's frozen contract; both headers are owned by other tasks). Without the pointer, the only way to
   halve weight memory from my side would be to point `Linear.W` at bf16 storage, which breaks `linear.h`'s documented
   "W is `[out][in]` fp32" contract and `test/test_linear.c:269` (`f.lin.W = W` with an fp32 buffer) — I did not do that.

Everything else of item 1 *is* mine and is ~80 lines: `gemm.c`/`gemm.h` (a `gemm_bf16()` on `cudaGemmEx` with
`CUDA_R_16BF` A/B, fp32 C, `COMPUTE_32F`, plus a `cublas.c:145`-style qualification check — extents/leading dims/strides
multiples of 8, 16-byte-aligned bases — and an fp32 fallback), `model.c` (the bf16 arena) and `linear.c` (cast the
activation operand with the new kernel, then `gemm_bf16`).

**What bf16 buys on those shapes** (standalone cuBLAS benchmark, `/tmp/gemmbench.cu` on gpubox, `-arch=sm_120`, the two

```
shape 0: M=4200 N=3584 K=1024 (y = x W^T)      shape 1: M=4200 N=1024 K=3584 (dx = dy W)
  fp32+FAST_TF32      0.277 ms   111.2 TFLOPS    0.305 ms   101.1 TFLOPS
  bf16 A/B,COMPUTE_32F 0.154 ms  200.2 TFLOPS    0.162 ms   190.2 TFLOPS   <- 1.8x, the item's win
  fp32+FAST_16BF      0.284 ms   108.7 TFLOPS    0.304 ms   101.3 TFLOPS   <- no win at all
mixed A=f32/B=bf16 (either order): CUBLAS_STATUS_NOT_SUPPORTED (15)
```

So the cheap route — `CUBLAS_COMPUTE_32F_FAST_16BF` with fp32 operands, no kernel and no header change — is worthless:
real cuBLAS does not down-convert, and a 20-step jefftrain run with it was **1.081 s/step**, identical to TF32 (its
losses did change, so the mode was accepted and used; it just runs the same fp32/tf32 kernels). Only genuine bf16 A/B
operands reach the 200 TFLOPS path, which is exactly why the cast kernel is unavoidable.

**Projection if unblocked** (for whoever re-cuts this): 0.126 s of W-GEMM at 111 TFLOPS → 0.069 s at 200 TFLOPS, minus
the activation casts (≈ 2.8 G elements of fp32-read + bf16-write per step ≈ 17 GB ≈ 15 ms) → **≈ 0.04 s/step saved, i.e.
1.081 → ~1.04 s/step (~4%)**, plus the memory half: weights 1.99 GB fp32 → 1.00 GB bf16, peak 11.33 → ~10.3 GB (which is
what M8 item 4, `--no-recompute`, wants). Numerics must stay in the non-exact mode only: the bf16 GEMM would replace
TF32, and exact mode must keep today's fp32 path so M6.2's trace stays bit-identical (M6.2 is only green because exact
mode is untouched — in TF32 the same 20 steps already miss step 5's 1e-3 gate at 1.31e-03, plan M6.2). M6.1's tf32 run
would then need re-measuring against the 0.05/158 gate; 0.0014 today, expect ~0.003–0.01.

A storage-only variant (bf16 weights + per-call widening with the existing `jt_bf16_to_f32_n`) needs neither missing
piece, but it is **not** a speed change: it halves weight memory and costs ~1% of step time, and it still needs the bf16
weight pointer to avoid lying about `Linear.W`.
