Two other decisions the frozen interfaces forced:

* **The residual add.** `linear_fwd`'s first GEMM has `beta = 0` (design §4.2), so it cannot accumulate into a residual,
  while `src/layer.h` says `x_out` MAY alias `x_in`. So `out_proj` lands in a work buffer, then `x_out` receives a copy of
  `x_in` (`cudaMemcpyAsync`, device-to-device, on `ctx->stream`; skipped when the pointers are equal) and
  `jt_add_inplace(x_out, out, n*1024)`. Costs one extra pass over `n*1024` floats, and it is the only form that is
  correct in both aliasing cases.
* **Buffer lifetime.** A bwd takes its temporaries from the back of the arena and gives them back before returning; this
  fwd does the same with `jt_work_mark` / `jt_work_restore`, including on the error path. Releasing the words while the
  kernels that read them are merely *ordered* on `ctx->stream` is the arena's rule (`src/linear.c` does the same): any
  later user of those words is queued behind them on the same stream.

### The one decision worth flagging: the q/k/v split is a copy

The plan says "split into q/k/v views (no copy; `[N][6144]` with q at column offset 0, k at 2048 and v at 4096; the l2norm
kernel takes a row stride)". **The l2norm kernel does not take a row stride, and neither does `gdn_fwd`.** `kernels/norm.h`
takes `rows, d` only and `k_l2norm_fwd` indexes `row * d`; `kernels/gdn.h` takes `q` as `[N][H][DIM]` with no pitch, and
`gdn_fwd_kernel` indexes `((t*H) + h)*DIM`. A view with stride 6144 would be read as garbage from the second token on, and
adding a stride would mean a kernel change, which plan rule 4 keeps out of this task's reach (`cuda-shim/` and
`kernels/` are other owners' files, and my file list is `src/layer_gdn.c` only).

The cheapest correct substitute, with no new kernel and one launch: `jt_to_head_major(cv, ck, n, /*heads*/ 3, /*head_dim*/ 2048)`,
the already-tested `[rows, heads*head_dim] -> [heads][rows][head_dim]` plumbing kernel (plan M2.1). With `heads = 3` its
output `ck` is exactly the three contiguous `[n][2048]` slices in q, k, v order — `ck[0 .. n*2048)` is q, then k, then v —
which is precisely the layout `l2norm_fwd` (rows = `n*16`, d = 128) and `gdn_fwd` want. It is one pass over the same
`3 N 2048` floats that the l2norm and the recurrence then read anyway, so it is not the M4.3 forward's cost.

**Doc consequence (not fixed here, because `docs/` is outside my file list):** plan M4.3 item 3's parenthetical should say
"split *via* `jt_to_head_major` with heads = 3 (a copy into three `[n][2048]` slices: the l2norm and GDN kernels take no
row stride)", or `kernels/norm.h`'s l2norm and `kernels/gdn.h`'s `gdn_fwd` should grow a pitch. The second is a kernel
change and a design change, not a fix for this task.

### What JT_FWD_SAVE keeps (and why each)

Exactly what design §4.8 reads, nothing else. Floats per packed token in brackets:

| saved | for |
|---|---|
| `a` [1024], RMSNorm's `r` [1] | the five `linear_bwd`s' `x`, the RMSNorm bwd |
| `uqkv` [16], `uz` [16] | `in_proj_qkv` / `in_proj_z`'s `linear_bwd` (`u`); `in_proj_a`/`b` are frozen and have none |
| `aa` [16], `beta` [16], `g` [16] | `k_gdn_gates_bwd`'s `aa`/`beta`, `gdn_bwd`'s `g`/`beta` (design §4.8's last two lines) |
| `pre` [6144] | `conv_bwd` (`dpre = dout * dsilu(pre)`) |
| `ck` [3 x 2048] | `l2norm_bwd`'s `x` (q, k pre-normalisation) and `gdn_bwd`'s `v` |
| `qkn` [2 x 2048], `rq`/`rk` [16] each | `gdn_bwd`'s `q`, `k`; `l2norm_bwd`'s `r` |
| `z` [2048], `o` [2048], `ro` [16], `y` [2048] | `gated_rmsnorm_bwd`'s `z`/`x`/`r`; `out_proj`'s `linear_bwd` takes `y` as its `x` |

`bb`, `qkv`, `cv` and `out` are work temporaries in both modes: design §4.8 derives everything they would say from
`beta`, `pre` and `y`. Per-token totals: **SAVE 23,681 + work 13,328 = 37,009 floats/token**, i.e. 2.66x inside
`JT_ARENA_FLOATS_PER_TOKEN` (98,304); a `JT_FWD_ONLY` pass puts all 37,009 in the work half, same sum. The arena overflow
check in `jt_save_alloc` / `jt_work_alloc` would have caught it, and did not fire.
