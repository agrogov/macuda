## What each script does, and why each choice

### `scripts/timing.sh` (plan M6.3)

`tools/jeff_lora/cuda/timing.sh` is the model: for each batch size it runs 100 steps, reads the `step N/100  X.XXs`
lines, drops steps 1–3 (compile and allocator warm-up) and prints

```
TIMING batch 8: 0.312 s/step (97 samples) -> 25.6 rows/s -> one epoch of 28645 rows ~18 min + dev checks
```

so this script prints **that same line**, same regex, same warm-up rule, same 28,645-row extrapolation, and then two
lines of its own: `peak … GB  N step(s) at … rows/s` from the run's `report.json`, and the plan's comparison
`… s/step vs PyTorch 0.143 (N.NNx), D§15 target < 0.400 -> within target | OVER target by …`.

* **Full train split**, as the plan says (`--train $DATA/train.jsonl`, no `--train-rows`): the step cost depends on the
  packed batch's token count, and the 4000-row sample the kit times is not the distribution §15's target is stated for.
  Tokenising those 28,645 rows is prep and is not in the TIMING number (the step lines are).
* **Batch 8 only by default**, because that is §15's batch (batch 16 pages WSL to host memory and drops to
  3.6 s/step). `BATCHES="8 16"` times both, each with its own prep and run directory.
* **`--dev-rows 64`**, the kit's, so the clock is not dominated by dev checks. `--log-every 1` is required: the TIMING
  parse needs every step line, not train.py's steps-1-3-then-every-25th rule.
* **The compute mode is checked, not assumed.** `gemm_init()` prints `gemm: tf32` or `gemm: exact fp32` once; the
  script greps the log for the mode it asked for (`EXACT=0` → TF32, the mode §15's target is for) and fails the
  measurement if a stale env timed the other one — the same trick `parity-eval.sh` uses.
* **Speed is reported, not gated.** Plan M6.3: "Being slower than PyTorch is expected for v1 and is not a failure.
  M8 is where speed gets work." So a number over 0.4 leaves exit 0 and says `OVER target … (v1: expected; M8 is the
  speed milestone)`. What does fail is a broken measurement: the run exits non-zero, the mode is wrong, or there are
  no step lines to average.
* Same shapes as `parity-eval.sh`: run from `train/jeff`, `export JT_REMOTE=macuda-train/wt-J34` first (parallel tasks
  must not share one), one ssh session, logs and `report.json` under
  `~/CLM-8B/data/ovril_detect/runs/jefftrain-timing-<UTC stamp>/b<batch>/` (plus a `jefftrain-timing-latest` symlink).

### `scripts/arm.sh` (plan M6.4)

`sh scripts/arm.sh soft` (the plan's run; `hard`/`balanced` use the same table as `arms.sh`) does the kit's arm, in the
kit's order:

1. `py/prep.py` — full train split at `--batch 8` (train.py's epoch order at `--seed 0`), **all** 1,722 development
   rows for the dev checks, and calibration + test as `--eval` splits. Every .jtb keeps its `.prep.json` sidecar, which
   jefftrain checks its own flags against.
2. `py/make_adapter.py` — the run's starting adapter. This is the one place the script has to work around the current
   tree: `src/lora.c` zeroes the flat buffer and `main.c` has no init of its own (its comment still says "or main.c's
   own init"), so a run without `--init-adapter` would never move (grad B needs A, grad A needs B). So the arm starts
   from design §10.1's fresh adapter: A ~ U(±1/√in), B ~ N(0,1)·1e-2, readout copied from the checkpoint. train.py
   starts at B = 0, so the first steps differ by one ~2e-2 LoRA update — orders inside the 0.01/0.02 gates, and stated
   in the script header so nobody has to guess. **Not a blocker for M6.4, but worth a line in the M8/M5 follow-up list.**
3. `jefftrain` — the arm's settings: `--init-adapter`, `--batch 8 --accum 1 --epochs 1`, `--eval-every 500`,
   `--eval calibration=… --eval test=… --eval-temperature 1`, `--targets soft --weights none`, `--lr 2e-4
   --readout-lr 5e-6`, `--log-every 25`. Output goes to `$RUN/c` and not `$RUN`, because jefftrain (like train.py)
   refuses a non-empty `--output` and `$RUN` already holds `prep/`.
4. `fit_temperature.py $RUN/c --calibration $DATA/calibration.jsonl` — CLM-8B's own, which is what `arms.sh` calls: it
   fits T on calibration and writes `pred-test-cal.jsonl` (and `temperature.json`) beside the T=1 predictions.
5. `score.py --test $DATA/test.jsonl "jefftrain-soft-T1=…/pred-test.jsonl" "jefftrain-soft=…/pred-test-cal.jsonl"
   --json $RUN/c/score.json` — CLM-8B's own, with the same `NAME=PRED.jsonl` arguments `arms.sh` and
   `fetch_and_score.sh` pass.
6. the Python side of the comparison: every `data/ovril_detect/runs/cuda-<arm>-*` on the box that has `report.json` and
   `pred-test-cal.jsonl` (for soft: `cuda-soft-20261108-165516` seed 0 and `cuda-soft-20261108-173754` seed 1) is
   scored with the **same** `score.py` and **same** test file into `$RUN/ref/`, so both sides are the same measurement.
7. design §10.3.3's gates, as a table plus one verdict line.

Why `fetch_and_score.sh` itself is not invoked: its job is to rsync a run named `cuda-<arm>-<TS>` to the Mac and then
overwrite `bench/ovril_detect/predictions/jeff-lora-<arm>.jsonl` and `scores_lora_cuda.json` — that is the Python arm's
own record, and overwriting it would destroy the reference this milestone is measured against. The scripts reproduce
its scoring step (`score.py` with the calibrated predictions next to the arm) and keep the JSON in the jefftrain run
directory instead. Nothing in CLM-8B's tracked tree is written.

The three gates, and how each is read:

| gate | source | value |
|---|---|---|
| dev soft CE at the chosen step | `report.json` `best_dev_soft_ce`, both sides (all 1,722 dev rows) | \|Δ\| ≤ **0.01** (design §10.3.3) |
| test soft CE | `score.py` `jev_soft_ce` on the **calibrated** 160-row predictions, both sides | \|Δ\| ≤ **0.02** (design §10.3.3) |
| `score.py` metrics | every column of its table: `jev_argmax_agreement`, P/R/F1/kind@0.5, P/R@0.9, maybe-cards, and the tp/fp/fn counts behind them | \|Δ\| ≤ the **two-seed band** |

"The two-seed band" is taken literally: for each metric, the spread (max − min) across the Python runs of the same
arm, i.e. the same arm at `--seed 0` and `--seed 1` — design §10.3.3's "same arm, two Python seeds give the noise
band". Floored at the measurement's own resolution (one test line = one card = 1/160 for a ratio, 1 for a count) so a
metric whose two seeds happen to agree exactly is not silently required to be bit-equal. The floors touch only these
metrics; the two CE gates keep the design's 0.01/0.02 unchanged. The Python run used for the two CE gates is the one
whose `report.json` `args.seed` equals this run's `--seed` (same tokenised batch order), so the comparison is like for
like; `JT_PRIMARY_RUN` overrides that, `JT_REF_RUNS` replaces the reference list.

Reference numbers the run will be read against (CLM-8B `bench/ovril_detect/REPORT.md`, the two soft seeds):

| soft seed | best dev soft CE | calibration soft CE | test soft CE (calibrated) | test agreement | temperature |
|---|---:|---:|---:|---:|---:|
| 0 (`cuda-soft-20261108-165516`) | 0.4575 | 0.4738 | 0.4897 | 0.931 | 1.008 |
| 1 (`cuda-soft-20261108-173754`) | 0.4511 | 0.4737 | 0.4793 | 0.925 | 1.004 |
