| file | what |
|---|---|
| `src/st.h` | the API: `St *st_open(path)`, `st_close`, `st_count`, `st_tensor(st, i)`, `st_find(st, name)`, `st_get(st, name, dtype, ndim, …)` / `st_getv(…, const int *shape)`, `st_write(path, n, names, shapes, ndims, data)`, plus `StDtype` / `st_dtype_parse` / `st_dtype_name` / `st_dtype_size` |

## What it does

* **Read.** `st_open` mmaps the file read-only and returns pointers into the mapping — no tensor is copied, so opening
  the 1.63 GiB checkpoint costs nothing. Two layouts are handled, both found or excluded on gpubox:
  a `.safetensors` file, and a **model directory** — `<dir>/model.safetensors`, or, when
  `<dir>/model.safetensors.index.json` exists, every shard its `weight_map` names, opened in first-mention order and
  then cross-checked (an index entry a shard does not hold, or a missing shard, is fatal). Every tensor in the header is
  registered, so `--list` shows `visual.*` too, not only what the model loads.
* **Validated at load, not later.** `st_get` takes the dtype and the full expected shape; a name, dtype, rank or dim
  mismatch exits 1 naming the tensor, what the file has and what the caller asked for. Header parsing also rejects an
  unknown dtype, `data_offsets` outside the data section, offsets that disagree with `shape`, duplicate names, junk after
  the JSON object, and a header length that does not fit the file. Everything is `exit(1)` with a `st: <path>: …` line,
  like `CK()`/`CB()`: none of these is recoverable, and a half-parsed checkpoint must not reach the kernels.
* **Write.** Design §9.2 verbatim: keys sorted, `{"dtype":"F32","shape":[…],"data_offsets":[a,b]}`, header padded with
  spaces to a multiple of 8, u64 little-endian length, then the data. F32 only. A name needing JSON escaping, a duplicate
  name, an empty tensor or a NULL data pointer is refused rather than silently written.
  This is the file `py/compare_layers.py` reads back, so it was checked with Python's own loader (below).

One deviation from the plan's wording, forced by the checkpoint: `ST_MAX_DIMS` is 8, not 4. The plan's
`shape[4]` would reject `visual.patch_embed.proj.weight [768,3,2,16,16]`, which is a 5-D tensor in the same header the
reader parses. See "Design corrections" below.

## Design / plan corrections for J41

1. **Plan M1.3's `shape[4]` cannot hold the checkpoint.** `visual.patch_embed.proj.weight` is `[768,3,2,16,16]`, 5 dims,
  and the reader registers every tensor in the header (that is what makes `--list` show `visual.*`). Implemented as
  `ST_MAX_DIMS 8` in `st.h`. Design §3.2 does not state a dimension bound, so this is a plan nit — but a later reader
  that follows the plan literally would refuse a valid file.
2. **Design §3.2's "Everything else in the file (`visual.*`, `mtp.*`) is skipped"**: this checkpoint has **no** `mtp.*`
  tensor at all (473 tensors = 320 text + 153 visual). The skip rule is right; the mention of `mtp.*` is not backed by the
  file. Harmless, worth one word in the doc.
3. **Design §3.2's "about 80 lines of C"**: `src/st.c` is 799 lines (688 non-blank, not comment-only; 44 functions,
   most of them one-screen parsers), because the reader validates rather than trusts — dtype, shape-vs-offsets,
   duplicates, header junk, shard completeness, and one message per failure that names both sides — which is exactly what
   M4.2 needs from a loader. No behaviour change, just don't let a later task "simplify" it back to 80 lines.

Nothing else disagreed: readout is `weight [255,1024] BF16`, the conv is `[6144,1,4]`, the GDN norm is `[128]`, `A_log`
and `dt_bias` are `[16]`, `in_proj_a/b` are `[16,1024]`, `q_proj` is `[4096,1024]`, `o_proj` `[1024,2048]` — all as §3.2
says.

## Notes for the tasks that build on this

* **M4.2 (`src/model.c`)**: `st_open` accepts the model *directory* (`~/models/jeff-base`), so
  `st_open("~/models/jeff-base")` and `st_get(st, "language_model.layers.0.linear_attn.in_proj_qkv.weight",
  ST_DTYPE_BF16, 2, 6144, 1024)` is the whole load path; `st_getv` takes the shape as an array when it is built at run
  time. `st_get` returns a pointer into the mapping: converting bf16 → fp32 on the card via `bf16_to_f32` is the only
  copy. `readout.safetensors` is a second `st_open` (it is not in `model.safetensors`).
* **M2.6 (`src/lora.c`)**: `st_write` is F32-only and sorts keys, so an adapter saved by jefftrain has the same key set
  and layout as Python's `save_file` but is written by hand; `st_open` already reads a Python-written
  `adapter_model.safetensors` (F32) and a bf16-or-fp32 `readout.safetensors` (the dtype is in the file, `st_get` states
  what is expected, so a variant has to be asked for explicitly).
* **M1.4 (`src/jtb.c`)** can copy this file's shape: one `mmap`, a validating pass, then pointers into the mapping; the
  `mkdtemp` fixture pattern in `test/test_st.c` is what `test_jtb.c` needs for its fixture, and a test binary with no
  arguments must exit 0 (README).
* Sharding is implemented and unit-tested (two synthetic F32 shards + a hand-written index in `test/test_st.c`), but the
  real checkpoint is a single file, so nothing else depends on it. If a sharded checkpoint ever appears, `st_open(dir)`
  handles it; `--list dir` will then print the shards' tensors in weight_map order.
* No card run was made, no `TINYNV_HW`, nothing in `cuda-shim/`, `vendor/`, `docs/`, the `Makefile` or another task's
  files was touched. `git status --porcelain` shows exactly the three files above (`build/` and `*.safetensors` are
  git-ignored).
