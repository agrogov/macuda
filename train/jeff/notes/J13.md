## What the two directions do (as written in `ref/gdn.c`)

Forward, per row, per head, S = 0 at the row's first token: decay `S *= exp(g_t)`, `kv = Sᵀ k_t`, `delta = (v_t − kv) β_t`,
`S += k_t ⊗ delta`, `o_t = Sᵀ q_t` (design §3.6). Backward, per (row, head), `dS = 0` after the row's last token, tokens
last to first: `Sd = S_prev e`, recompute `kv`, `delta`, `S_t = Sd + k_t ⊗ delta`; `dq_t = S_tᵀ do_t` and
`dS += q_t ⊗ do_t`; `dk_t = dSᵀ`-style `sum_j dS[i,j] delta[j]` and `ddelta = sum_i dS[i,j] k_t[i]`; then `dv = ddelta β`,
`dkv = −ddelta β`, `dbeta = sum_j ddelta_j (v_j − kv_j)`; **then** `dS += k_t ⊗ dkv` and `dk_t += sum_j Sd[i,j] dkv[j]`;
**then** `dg = sum_{i,j} dS[i,j] Sd[i,j]`; **then** `dS *= e` (design §4.8, including its "The order matters" note —
`dk_t`'s first term and `ddelta` read dS before the `k ⊗ dkv` term, `dg` after it). Inner sums accumulate in `double`
and round once, the rule `ref/real.h`'s `r_*` wrappers follow: 16384-term fp32 sums (`dg`) would otherwise carry an
order-dependent error of their own into the 1e-4 kernel gate.

S_prev: the backward keeps design §8.3's **64-token checkpoints** (the state at every 64th token, written before that
token's step, so segment 0's checkpoint is all zeros) and replays one segment forward into a `[64][Dk*Dv]` scratch to get
the S_prev of the tokens inside it — the kernel's own `ckpt`/`sp` scheme, which also keeps the oracle usable at the
model's dims: `(N/64)·H·Dk·Dv` reals instead of `N·H·Dk·Dv` (84 MB instead of 5.3 GB for the plan's biggest M3.2 batch).
There is one forward-step function (`gdn_step`) for both directions and one replay function (`gdn_row_run`, which either
writes checkpoints or writes a segment's S_prev), so a stored S_prev cannot disagree with the forward.

## Two bugs this group found while it was being written (why it is not vacuous)

1. The first draft kept **one** S matrix per row and stepped all H heads through it, and its backward walked heads
   outermost. With H=1 that is indistinguishable from the design, and `dq` passed even at H=2 (it is checked against the
   FD of whatever forward is written), but dk/dv/dg/dbeta came out at rel ≈ 0.3–0.9: the reverse pass was not the
   reverse of the interleaved forward. The design's state is **per (row, head)**; fixing both directions to keep/prepend
   one state per head fixed it (the `plan` case's numbers above). This is exactly the kind of error the H=2 shape is
   there for, and why the extra `ckpt` case exists.
2. An early `gdn_forward_history()` leaked its `delta` scratch per token; the `ckpt`/replay split removed the whole
   dense-history path.

Throwaway mutated copies of `ref/gdn.c` (in `/tmp`, compiled against the same fixture, deleted afterwards; the repo was
never mutated) — each is caught by exactly the gradient it should be:

| mutation | caught by |
|---|---|
| `dS *= e` dropped (dS never decays) | dk, dv, dg, dbeta on **all five** shapes (rel 0.03–1.7); `dq` **not** caught |
| `dk`'s `sum_j Sd[i,j] dkv[j]` term dropped | `dk` only, on all five shapes (rel 0.04–0.18) |
| `dg` computed from `S_prev` instead of `Sd` (i.e. skipping the decay) | `dg` only, on all five shapes (rel 0.24–1.4) |

(`dq` surviving the first mutation is honest: dq depends on `S_t`, not on the carried `dS`. The value of five separate
gradients is that each of them pins one part of the reverse pass.)

## Notes for M3.2 / M3.3 (the kernel and its tests, J16/J17)

* The declarations are `ref/gdn.h`'s, unchanged from plan M3.1. Layouts: `q,k` `[N][H][Dk]`, `v,o` `[N][H][Dv]`,
  `g,beta` `[N][H]`, `off[B+1]`, token-major (the layout of the conv output slices, design §8.3).
* **State is per (row, head)** and starts at 0 at each row's first token; `dS` is 0 after each row's last token and is
  carried only within one (row, head). The kernel's grid is (B, 16, 4) so that falls out; the reference is the check.
* The five gradients the plan's `test_gdn bwd` gate names are `dq, dk, dv, dg, dbeta`; `dq/dv/dg/dbeta` are written once
  per (token, head) (never accumulated across tokens), only `dk` sums two terms and only `dS` is carried.
* `ref_gdn_bwd` uses design §8.3's 64-token checkpoints internally, so "compare `sp` for segment 0 with the ref's stored
  S_prev" (plan M3.3 step 1) is now a *kernel-vs-kernel* check: the reference does not expose its checkpoints. If that
  comparison is wanted, the honest oracle is the reference's own replay formula (`Sd`, `kv`, `delta`, `S_t` above) — or
  ask me to expose the checkpoint buffer; the header is deliberately unchanged from the plan.
* `ref_gdn_bwd` is the adjoint of `ref_gdn_fwd` as written (`ref_gdn_fwd` is the FD closure), so the two must be
  compared as a pair: a kernel that reproduces `ref_gdn_fwd` to 1e-4 and, independently, `ref_gdn_bwd` to 1e-4 is
  consistent with these.
* Gates: nothing in `test/harness.h` was touched — `JT_TOL_FWD 1e-5`, `JT_TOL_BWD 1e-4`, `JT_TOL_GRAD 1e-6`.
* No real data (plan rule 5): every input is `rnd_fill` from a fixed seed.
