## The change (one file, `src/head.c`)

The backward in design §4.1's order, with the call each step uses:

| step | call |
|---|---|
| `dR += dlogits^T z` → `grad + readout_off` | `gemm(1, 0)` M = 255, N = 1024, K = B, `beta = 1` (accumulated) |
| `dz = dlogits R` | `gemm(0, 0)` M = B, N = 1024, K = 255 — the transpose problem of the forward's `gemm(0,1)` |
| `dhN[off[b+1]-1] = dz[b]` | `jt_zero(dh, n*1024)` + one `cudaMemcpyAsync` (D2D) per row: the mirror of the forward's gather |
| `dres = RMSNormBackward(dhN)` | `rmsnorm_bwd(x, final_norm, dh, r, dres, n, 1024, zero_centred = 1)`, `r` from the saves |

Everything the backward reads is the forward's saves, indexed from the arena's base in the order `head_fwd(SAVE)` took
them (J23's contract, unchanged): `r [n]`, `z [B][MT_HIDDEN]`, `dlogits [B][MT_READOUT_OUT]` (zero-padded to the
readout's 255 columns, so the width does not need `n_opts`). Both temporaries come from the arena's work half and are
given back before returning (design §6.2, src/layer.h) — no allocation anywhere.

Three things worth writing down:

* **`dR` is accumulated (`beta = 1`), not written.** A parameter gradient belongs to the optimizer step, not to the head,
  exactly like `linear_bwd`'s `dA`/`dB` (src/linear.h). The test below checks it by calling `head_bwd` twice and looking
  for `2 x` the reference.
* **`dhN` is dump_ref's `grad.final`, and it is readable after the call.** `head_bwd`'s frozen signature has no room for
  the gradient at the final norm's *output*, and it does not need one: `dh` is the first (and only) work-half allocation
  the backward takes, so for a mark read before the call it sits at `ctx->arena + mark - n * MT_HIDDEN`, and
  `jt_work_restore` moves the cursor back, not the data. That is now documented in `src/head.c`'s header comment as the
  way a test — or M5.2's `--dump-backward`, which must write all 403 ref keys — reads `grad.final`. Every later
  allocation in a bwd starts *below* it, so the address is stable.
* **Argument checks return `JT_LAYER_FAIL` with a message**, like the forward: null context/model/parameter
  buffer/x/b/dres, `b->rows` outside `0..JT_MAX_ROWS`, `b->off[rows] != n`, a row of length 0 (the head's last token is
  `off[r+1]-1`, design §7, so an empty row would read the previous row's token), a missing gradient array, a readout
  outside the flat buffer, and saves larger than the arena (i.e. "was `head_fwd` run in SAVE mode?"). An empty batch is
  `JT_LAYER_OK`. `head_bwd` does **not** synchronise the stream (the forward's `loss` read-back stays the only
  synchronisation in this file).

## Numbers worth recording for the later tasks

* **Cost.** Backward: 2 GEMMs (255 x 1024 x B and B x 1024 x 255), one `jt_zero` of `n` x 1024 floats, B D2D copies of
  4 KB, one `rmsnorm_bwd` over all `n` tokens. At the plan's batch (B = 8, N = 4200) that is 2 x 2.2 MFLOP of GEMM next
  to one layer's 30.8 GFLOP projections, plus 17 MB of zeroing — the head's backward is noise on both.
* **Arena.** The saves are `n + B*1024 + B*255` floats: **2,665 floats (10.7 KB)** for the fixture, **14,432 floats
  (58 KB)** at B = 8 / N = 4200 — the same number J23 recorded for the forward, and `head_bwd`'s temporaries (`dh` and
  `dz`, 18,432 floats at that shape) come out of the work half and go back.
* **For M5.2 (`--dump-backward`).** `grad.final` is written by reading
  `ctx->arena + jt_work_mark(ctx) - n*MT_HIDDEN` after `head_bwd` returns (for a mark taken before the call, in SAVE
  mode, with `dres` in a caller buffer); `grad.layer.23.out` is `head_bwd`'s `dres` and `grad.readout` is
  `ctx->lora->grad + ctx->lora->readout_off`. All three must be dumped after `head_bwd` and before the layer loop's next
  `jt_saves_reset`. The order to run them in is head first: `model_forward` (FWD_ONLY) → `head_fwd(SAVE)` →
  `head_bwd` → `layer_fwd(SAVE)`/`layer_bwd` for i = 23..0, and the head's saves are then at the arena's base because it
  is the first SAVE pass.
* **The LoRA half of the flat gradient buffer stays exactly 0** (`max|.| 0.000e+00` over 10,223,616 values) when only the
  head runs, so M5.1 items 2-4 do not have to distinguish the head's contribution from theirs.
* `grad.final`'s magnitude is small (max 6.5e-03) while design §10.2's metric is relative to `max|b|`, so the gate is as
  tight there as on the larger `grad.layer.23.out`: the 1.5e-06 above is 1.5e-06 of 6.5e-03, i.e. ~1e-08 absolute.
