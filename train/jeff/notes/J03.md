# J03 — M1.1–M1.2: row-major GEMM wrappers and their test

Plan: M1.1 (`src/gemm.c` + `src/gemm.h`), M1.2 (`test/test_gemm.c`). Design §5 (the issue mapping and the compute

M1.2a (the card checkpoint for the GEMMs) is **not** run here: it is the separate card `G-m1`. The binary it will run is

## What was built

`src/gemm.h` — `gemm_init()`, `gemm_is_exact()`, `gemm()`, `gemm_batched()`, with the design's signatures verbatim
(`long` strides).

`src/gemm.c` — design §5's single issue of the transposed problem, written out once:

```c
cublasGemmEx(h, tb?T:N, ta?T:N, N, M, K, &alpha, B, CUDA_R_32F, tb?K:N, A, CUDA_R_32F, ta?M:K,
             &beta, C, CUDA_R_32F, N, COMPUTE, CUBLAS_GEMM_DEFAULT);
```

(`m=N, n=M, k=K`; the cuBLAS "A" argument is our `B`, the cuBLAS "B" argument is our `A`; the leading dim is always the
stored row length, `N` for C.) `gemm_batched` is the same mapping through `cublasGemmStridedBatchedEx`, with the strides
following their own matrices — our `B` gets `sB` because it is the cuBLAS "A" argument (plan M1.1). `alpha`/`beta` are
values in the API and host pointers to cuBLAS (default pointer mode). Both are wrapped in `CB()`.

Compute mode: a file-static `cublasComputeType_t` set in `gemm_init()` — `CUBLAS_COMPUTE_32F` when `JT_EXACT` was given
at compile time (`-DJT_EXACT=1` and `-DJT_EXACT` both work; `-DJT_EXACT=0` leaves the run-time switch live) or when
`getenv("JT_EXACT")` is `"1"`, else `CUBLAS_COMPUTE_32F_FAST_TF32`. It prints `gemm: exact fp32` / `gemm: tf32` once.
`gemm()`/`gemm_batched()` call `gemm_init()` themselves, so the mode is decided exactly once even if a caller forgets;
`gemm_is_exact()` is what the test picks its gate from, so one binary serves both card-check steps.

`test/test_gemm.c` — `ref_gemm`, a double-accumulator `i-k-j` triple loop over transposed-to-contiguous `[M,K]`/`[K,N]`
copies (so `ta`/`tb` change the reference's input layout, not its inner loop), fixed xorshift32 seed 2463534242,
inputs uniform in [-1,1), metric `rel = max|got-want| / max(1e-30, max|want|)`, a non-finite result is `INFINITY`
(a failure). Gate `1e-5` in exact mode, `5e-3` under TF32 — read from `gemm_is_exact()`, not assumed. Cases:

* `gemm`: all four `(ta,tb)` × sizes `(1,1,1) (7,13,5) (64,64,64) (130,17,1024) (4200,16,1024) (16,1024,4200)` ×
  `alpha ∈ {1,2}` × `beta ∈ {0,1}` (C prefilled, so `beta=1` means something) = 96.
* `gemm_batched`, batch 8 (the 8 query heads), strides `sA = M*K`, `sB = K*N`, `sC = M*N`: `(ta,tb) = (0,1) (0,0) (1,0)`
  × sizes `M=L, N=K=256` for `L ∈ {37, 300}` × `(alpha,beta) ∈ {(1,0),(2,1)}`, **plus** the two real attention shapes
  of design §5 — scores `M=L, N=L, K=256` `(0,1)` and `P·V` `M=L, N=256, K=L` `(0,0)` — = 16.
* 112 cases in all. One line per case, then `GEMM OK n/n`; any failure prints `FAIL …` and ends with `GEMM FAILED
  passed/total`, exit 1.

On the shim's null device (`-DJT_SHIM`, and not both `TINYNV_HW`/`TINYNV_SOCKET`) every one of the 112 calls is still
issued and checked by `CK`/`CB`, the numbers are not compared, and the run prints `GEMM OK (null device: launch only)`
and exits 0 — the README convention `make test-null` relies on.

## Notes for the tasks that build on this

* Call `gemm_init()` once at start-up (it prints `gemm: exact fp32` or `gemm: tf32`), then just `gemm(...)` /
  `gemm_batched(...)`. Forgetting it is harmless: the first GEMM call initialises the mode itself.
* `gemm_is_exact()` is the supported way to pick a gate (`1e-5` vs `5e-3`); don't test `getenv` in a test.
* Argument order for the callers (design §5's table): `y = x W^T` is `gemm(h, 0, 1, N, out, in, 1, x, W, 0, y)`;
  `dx = dy W` is `gemm(h, 0, 0, N, in, out, 1, dy, W, 0, dx)`; `dB += s dy^T u` is `gemm(h, 1, 0, out, 16, N, s, dy, u, 1, dB)`.
  `beta=1` accumulates into C; `alpha`/`beta` are values, not pointers.
* `gemm_batched`'s strides are element counts and follow their matrix: pass `M*K` for A, `K*N` for B (even when the
  cuBLAS "A" slot receives B), `M*N` for C.
* For M1.2a: on the Mac null device, all 20 `cublasGemmStridedBatchedEx` cases in the TF32 step returned
  `CUBLAS_STATUS_SUCCESS` (no `CB` error), i.e. libtinycublas's type contract accepts fp32 A/B/C with
  `CUBLAS_COMPUTE_32F_FAST_TF32` through the strided-batched entry point as it does through `GemmEx`. That is a null-device
  answer to design §12's open question only — the card's answer is what G-m1 records. On the card the same binary runs
  twice (exact, then TF32) and must print `GEMM OK 112/112` both times.
* `test_gemm` with no arguments runs everything on purpose: that is what `make test-null` and `card-check.sh` call.
