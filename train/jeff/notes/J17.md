## What the kernel is

Per block (row b, head h, column tile): warp w owns key rows `i` in `[64w, 64w+64)`, lane l owns value column
`j = tile*32 + l`. A thread therefore holds a 64-float piece of every 128x128 matrix the reverse pass touches, and its
piece of `dS` — `ds[64]` — stays in registers for the *whole row*, carried from the row's last token back to its first and
across segment boundaries. Segments run last to first; each is two passes:

* phase A, recompute: load S from `ckpt[b][h][seg]`, run D§3.6's step for the segment's tokens, and before each step write
  the thread's 64 values of S_prev to `sp[tl][i][j]` (global, 1 MB per block).
* phase B, reverse: D§4.8's lines for the segment's tokens last to first, re-reading S_prev from `sp` **once per token**
  into `sd[64]` (the plan's budget allows `ds` + `sd`; `sp[64]`/`st[64]` are never declared — `st_i` is rebuilt inside
  the butterfly loop that uses it).

Reductions: `kv_j` and `ddelta_j` are sums over all 128 key rows, so each warp sums its 64 and the block adds the halves
through `__shared__ kvp[w][lane]` **in the fixed order 0 then 1**; `dq_i`, `dk_i`, `dbeta` and `dg` are warp butterflies
(`gdn_warp_sum`, the plan's `warp_sum`) with lane 0 (and warp 0) storing. No `atomicAdd` anywhere, so no result depends on
the schedule (design §8.1). dv needs no reduction: value column j belongs to exactly one tile.

Register discipline (plan M3.3's "read before writing phase B"), measured with `-Xptxas -v` after every change:

| body | registers | spill stores / loads |
|---|---|---|
| phase A + phase B, `ds[64]` + `sd[64]` live, seven separate unrolled 64-row loops per token | **168** | **0 / 0** |

Neither of the plan's two fallbacks was needed: `sd[64]` fits alongside `ds[64]`, so `sp` is read **once** per token
instead of in each of the four loops that want it, and 64 rows per warp fits, so there is no 4-warp split of D§8.3.

168 registers * 64 threads = 10752 of an SM's 65536, i.e. 6 blocks (12 warps) per SM, 256 bytes of smem. Two warps per
block were enough: **D§8.3 does not need the 4-warp variant**, so there is nothing to change there for J41 on that count.

Order of work. The plan's M3.3 asks for three stages (phase A alone, then dv/dq, then the rest), each tested before the
next. The kernel here was written in one pass instead — the three stages share `ds[64]`'s lifetime and the same register
budget, so building them separately meant writing the loop shell twice — and each stage is then *isolated* by the checks
rather than by the order of authorship: phase A alone by `gdn_bwd_sp`/`gdn_bwd_sp_ckpt`, the do terms alone by the `dq`
and `dv` lines (both pass on batches where the mutations below break only dk/dg/dbeta), and dk/dg/dbeta individually by the
mutation table below.

## Where the 11.6 ms goes — a finding for J41 (design §8.3, not the plan)

The kernel is **memory-bound, and the traffic is D§8.3's sp scratch**, not the arithmetic:

* phase A writes S_prev for every token: 4096 floats per block per token = 16 KB, and a token is covered by 4 tiles x 16
  heads = 64 blocks, so **1 MB of sp per token**. At N = 5094 that is **5.3 GB written + 5.3 GB read** (the kernel reads
  each token's slice exactly once — that is what `sd[64]` buys; re-reading it in all four loops, the plan's no-`sd`
  fallback, would double the read side).
* the 4-tile partials are `[4][N][16][128]`: 668 MB each for dq and dk, **written 1.3 GB, read 1.3 GB, final 334 MB**
  across the reduce.
* dv, q/k/v/dout/g/beta reads and the checkpoint loads add ~0.1 GB.

That is ~13 GB per call against a 5090's 1.79 TB/s peak: **7.3 ms is the floor for this structure**, and 11.6 ms is ~63% of
peak (a plain copy reaches ~85%). The arithmetic is not the limit — ~1500 warp-instructions per token gives ~0.5 ms. So
D§8.3's "about 2 ms per layer for fwd + bwd" cannot be met by any kernel that stores S_prev for every token in global
memory: 10.7 GB in 0.7 ms would need 15 TB/s. Removing the current sp traffic entirely and keeping everything else would
already be ~3 ms; keeping a whole segment's sp resident in L2 (a chunk of 8 tokens is 128 KB per block, so all 512 blocks'
live window is 64 MB) or in shared memory (a rolling window replayed from the checkpoint per chunk, ~25% more phase A
work) is where the next 4x is. **Both change D§8.3's `sp[tl][64][128][32]`, global, 1 MB per block — which is why this
task did not do it.** It belongs to J41 (design §8.3) and/or M8's chunked GDN, with
`gdn_bwd_sp_floats()`/`gdn_bwd_part_floats()` in `kernels/gdn.h` as the only place a buffer size is written down.

The 2.8 ms that the ragged batch costs on top of the uniform one *after* scaling for the token count (7.25 ms x
5094/4160 = 8.9 ms) is the tail: `gridDim.x = B` puts row 0's 1026 tokens on 64 of the 512 blocks while the rest finish,
so the critical path is the longest row, not the mean. A second-order effect; it is not worth a grid change on its own.

## `test/test_gdn.c`'s new checks (beyond the five numbers)

* `gdn_bwd_sp b=… h=… tile=… seg=0` — phase A's scratch against a **double-precision host replay** of D§3.6 started from
  the kernel's own checkpoint (`replay_segment_sp`), for one block of the last row. This is the plan's step 1 in its honest
  form: `ref_gdn_bwd` keeps its S_prev copies internally and does not expose them (J13/J16 notes), so the replay is what
  an independent phase A looks like. Note it is checked on segment 0 — the last phase A a block runs — because that is
  what sp holds when the call returns.
* `gdn_bwd_sp_ckpt` — sp's `tl = 0` slice against the segment-0 checkpoint, which is exactly zero: proves the block wrote its
  slice at all, since the whole 512 MB scratch is `cudaMemset`-filled with `0x7f` before the launch.
* every output buffer (dq, dk, dv, dg, dbeta, sp) is garbage-filled before the call, so a block that skipped a segment
  (a short row inside a batch whose longest row needs 17 of them) cannot pass by leaving a stale value behind.

Four mutations confirm the group is not vacuous (throwaway tree under `/tmp/mut` on gpubox; the repo was never mutated):

| mutation | caught by | where it shows |
|---|---|---|
| `dk_i` read from dS *after* the `k ⊗ dkv` term (D§4.8's order broken) | `dk` on 6 of 7 batches | rel 0.03-0.07 |
| `dg_t` read from dS *before* the `k ⊗ dkv` term | `dg` on 6 of 7 batches | rel 0.02-0.04 |
| phase A writes S_prev *after* the step | `sp`, `sp_ckpt`, and dq/dk/dbeta | rel 0.2-0.65, sp 6.7e+27 |
| `dbeta_t` without the 32-lane butterfly | `dbeta` on all 7 batches | rel 0.93-1.06 |

## Notes for whoever builds `src/layer_gdn.c` (M4/M5)

* `gdn_fwd(..., int nseg, float *ckpt, float *o, stream)` and then `gdn_bwd(..., int N, int nseg, const float *ckpt,
  const gdn_bwd_work *work, float *dv, float *dq, float *dk, float *dg, float *dbeta, stream)`: **the backward reads the
  forward's checkpoints**, so the forward must run with a ckpt buffer before it, and both calls must see the same `nseg` =
  `gdn_ckpt_segs(off_host, B)`. Allocate `ckpt` (142.6 MB at B = 8) plus the work buffers once
  (`gdn_bwd_sp_floats(8,16)` = 512 MB, `gdn_bwd_part_floats(N,16)` = 668 MB for each of dq_part/dk_part,
  `gdn_bwd_gate_floats(N,16)` = 1.3 MB for each of dbeta_part/dg_part) — 1.99 GB at B = 8 / N = 5094, which is the number
  design §6.2's memory plan has to carry.
* `gdn_bwd` takes the token count as a plain `int` (the reduce pass needs `N` and the device copy of `off` is not readable
  from the host) — the caller has it as `off[B]`.
* dq, dk, dv are `[N][16][128]`, dg and dbeta `[N][16]`, all written in full, so the caller can feed them straight to the
  l2norm/conv/gates backward. `g` in [-1,0] and a normalized `beta` are the only range assumptions, and neither is a
  precondition the kernel checks.
* If M8 or J41 shrinks the sp window, only `kernels/gdn.{h,cu}` and the allocation in the layer change; the numbers in
  `test_gdn bwd` are the gate to keep.
