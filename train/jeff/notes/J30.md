## The change

### The finding that shaped it: each bwd reads its saves from the arena's **base**

The three halves' backwards each index their save block from `c->arena` with no offset: `layer_mlp_bwd` binds
(`src/layer_mlp.c`'s `saves_bind(c->arena, n, &s)`), `layer_gdn_mixer_bwd` replays its walk from `c->arena`
(`saves_replay`), `layer_attn_mixer_bwd` too (J29's "the arena's base"). But `layer_fwd(SAVE)` runs the mixer first and
the MLP second, so one save half holds the mixer's block at the base and the MLP's above it — **a single `fwd(SAVE)` can
serve only one of the two backwards.** Each piece was tested (J27, J28, J29) with its *own* `fwd(SAVE)` as the first user
of the save half, which is why nobody saw this; the plan's `layer_fwd(SAVE)` → `layer_bwd` pairing is the place it shows
up, and that pairing is what this task owns.

So the layer's two halves are forward-passed again with their own saves at the base, in the order the layer's maths
requires (the MLP's path first — J29's trap: the mixer's `dy` must include it):

| file | function | what it does |
|---|---|---|
| `src/model.c` | `layer_bwd` | `jt_saves_reset` → `layer_mlp_fwd(SAVE)` → `layer_mlp_bwd`; `jt_saves_reset` → mixer `fwd(SAVE)` → mixer `bwd`. Correct for any caller, but costs a third forward when it follows a `layer_fwd(SAVE)`. |
| `src/model.c` | `model_backward` | design §6.2's sweep: for i = 23..0, the mixer's `fwd(SAVE)` from `saved_in[i]` (its output *is* `post_mixer`), park its save block, the MLP's `fwd(SAVE)` + `bwd` at the base, copy the park back, the mixer's `bwd`. One recompute forward per layer — design §6.2's "+33%", not "+66%". |
| `src/main.c` | `--dump-backward OUT` | the sweep plus the head's backward and the 403-key file. |

The park's size is read from the save cursor right after the mixer's `fwd(SAVE)` (`c->save_at`), so **no piece's save
layout is written down twice** and a later change to one (as J28's out_proj `u` was) cannot silently mismatch: the copy
is `mixer_saves` words whatever they are. Two device-to-device copies per layer (~24 K floats per token each way) buy
the whole second forward back. The arena's work half holds the park above every temporary the MLP's and mixer's bwds
take, so nothing can overwrite it before it is copied back; the cursor is reset with `jt_save_alloc(mixer_saves)` so the
mixer's replay sees the save watermark it checks.

`--dump-backward` is the forward dump plus the gradients, in the same file: `in.ids`/`in.off`, 24 x
`layer.{i}.in/post_mixer/out`, `final`, `logits`, `loss`, then `grad.layer.{i}.out` x 24, `grad.final`, the 300
`grad.{stem}.lora_A/B` and `grad.readout`. The forward keys are the forward sweep's (unchanged, bit identical — see
above); `layer.{i}.post_mixer` is the recompute's, because the mixer's `fwd(SAVE)` writes its output into the
`post_mixer` slab it is given (`model_backward`'s `post_mixer` argument), so the key costs nothing extra. The 300 LoRA
gradients and the readout are slices of the flat gradient buffer (`src/lora.h`), so one `dev_pull` of
`lora->grad` (10.5 M floats, 41 MB) yields all of them. `grad.final` is `head_bwd`'s `dh`, its first and only work-half
allocation, at `arena + mark − n*MT_HIDDEN` (`src/head.c`'s note); it is pulled **before** the layer loop, which takes
those very words for its scratch.

`grad.layer.{i}.out` is the value **on entry** to layer i's backward, copied out before the MLP's bwd writes `dres` in
place (J29's "the dump must not re-derive it"). The sweep's final `dres` (dL/d(the embedding's output)) has no
reference key — the same gap as J28's `grad.layer.0.in` — and is not dumped.

## TF32, and a number M5.2/M6 need

The same command without `JT_EXACT` (`gemm: tf32`) gives `87 ok, 316 failed`: `grad.layer.23.out` 7.4e-04 (fine) but
`grad.final` 7.97e-04 and then the gradient **grows by ~100x per layer** down the sweep — `grad.layer.20.out` 1.7e+01,
`grad.layer.12.out` 2.97e+09, `grad.layer.0.out` 1.258e+21 (max|.| 1.4e+20 against a reference scale of 0.11). That is
not TF32 noise in the code: a **1e-6 relative nudge to one entry of the entry gradient, run in exact mode**, reproduces
the same numbers almost digit for digit (layer 22 5.037e-01, layer 20 1.69e+01, layer 12 2.98e+09, layer 0 1.257e+21).
The sweep is an exact linearisation, and this fixture's model has a backward whose worst-direction amplification is
~1e21 over 24 layers, so any 1e-4-relative perturbation of the last layer's gradient arrives at layer 0 at O(1e20) while
the *true* gradient (0.0399 → 0.1115 over the same span) rides a stable direction. Consequences, which are not this
task's to fix:

* M5.1's/M5.4's gradient gates are exact-mode only (design §10.2, as J27 predicted for the FD gate) — `card-check.sh`'s
  `JT_EXACT=1 TINYCUBLAS_TC=0` is right.
* M6 (one training step bit-close to PyTorch, 5e-3 on gradients) will only be measurable in exact mode as well, i.e.
  **design §6.1's TF32 v1 precision is a question for the user before M5.2/M6 leans on it**: in TF32 the *early* layers'
  gradients of this model are noise by construction, and gradient clipping's norm / Adam's update inherit that.
* Recompute in a lower precision than the backward is the same problem (the recompute feeds the backward at a perturbed
  point); that is another reason v1 does the recompute in fp32.

## Numbers worth recording for the later tasks

* **Arena.** The park is `mixer_saves` words per layer, i.e. the *mixer's* save block (23,697 floats/token on a GDN layer,
  12,875 on an attention layer — J28/J29). Peak use of the backward is park + the MLP's saves + the MLP's and the
  mixer's bwd temporaries + two slabs ≈ **55–59 K floats per token against `JT_ARENA_FLOATS_PER_TOKEN`'s 98,304**, so
  the design's per-token budget still holds at N = 4200; measured at n = 1200 / lmax = 700 the ctx prints
  `arena 0.50 GB` and the sweep runs (`gdn nseg 11`). At the plan fixture the ctx is `arena 0.04 GB`.
* **Cost.** One forward sweep + one recompute forward + one backward per layer, i.e. design §6.2's "+33%" — the
  `--dump-backward` run on the 107-token fixture is **1.4 s wall including the 2.5 GB model load** (867 MB of that is the
  four flat buffers; the 403-key file is 84.9 MiB, its host copies ~75 MB).
* **For M5.2 (the step).** `model_backward(c, saved, n, &b, NULL, NULL, dres)` is exactly what a training step needs: no
  dump buffers, one extra forward, `dres` in as `head_bwd`'s result and out as dL/d(the embedding's output) (which has no
  parameters, so the step can ignore it). `lora_zero_grad` must run before `head_bwd` (both `dR` and every `dA`/`dB`
  accumulate with beta = 1). The `post_mixer` and `grad_out` slabs exist only for the dump.
* **For M5.4 (the card checkpoint).** `sh scripts/card-check.sh <A|B> m5` with `JT_REF` and `JT_DUMP_ARGS` set needs
  nothing new: it runs exactly the command above through the shim and prints `checkpoint m5: 1 steps, 0 failed`. Its
  fixture (n = 107) leaves the park at 2.5 M floats, far inside the arena the ctx sizes for the batch.
* **`layer_bwd` is correct but is not the hot path.** It recomputes both halves itself (2 forwards + the caller's), which
  is what a per-layer test wants; `model_backward` is why the trainer does not pay that. If someone later wants
  `layer_fwd(SAVE)` + `layer_bwd` to cost one recompute, the one-line fix is in J27's file: `layer_mlp_bwd`'s
  `saves_bind(c->arena, ...)` would have to take the mixer's block size into account (or `layer_fwd` would have to run
  the MLP's saves at the base and hand the mixer's block to the bwd some other way). Nothing in this task's files needs
  to change for that.
