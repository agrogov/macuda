## 2. What changed, and where the defaults live

**One place:** `src/main.c`'s `m8_defaults()`, called right after `gemm_init()` (so `gemm_is_exact()` is known) and
before `model_load()` (which reads `JT_BF16_WEIGHTS`). It sets a variable **only** when it is unset, prints one

**The store's auto rule** is `src/model.c`'s `store_auto_mode()` (the one bit-identical item, decided where the memory

  when the question is asked. The peak is unchanged; only the order of two allocations moved.
* Backend split, both measured: on **real CUDA** the answer comes from `cudaMemGetInfo`'s free count, because a probe

# J51 — G-m8probe finding 1: why the chunked GDN forward disagrees with the sequential kernels

`logs/jefftrain/G-m8probe.md` finding 1 filed this as its own card: on card B (RTX 4090, `ARCH=sm_89`,
`SHIM=cuda-shim/build/shim-sm_89`) `test_gdn` fails `gdn_fwd chunked_vs_sequential` at rel **0.000609 / 0.000661 /
0.142 / 0.000547 / 0.0742** against the 1e-4 gate, while gpubox on the same code and shape measures ~1e-6. It read as a
race or uninitialized memory because the numbers move between runs. **There are two independent defects, and the
"changes between runs" is neither a race nor uninitialized memory being re-randomised per run.**

1. **`gdn_chunk_trinv_kernel` never writes the strictly-upper part of `T = (I+L)^{-1}`, and every GEMM that uses `T` reads
   the whole CxC matrix.** So the chunked path reads arena memory that no kernel of the call wrote. On gpubox a fresh
   `cudaMalloc` is zero, so the read was invisible and the cross-check passed at 1.1e-6 (and stayed invisible, because the
   only thing ever written into that region is the lower triangle of the previous call's `T`). On the shim the arena is
   recycled video memory, and the leftover fires straight into the delta system, which amplifies it: this is the
   0.14-0.42 class of error, and it is **stable within one binary run** (same allocation, same leftovers) — the two
   G-m8probe logs differ because they are **two different GEMM cubins**, not two runs of one binary.
2. **`libtinycublas` ran every f32 GEMM on the TF32 tensor-core kernel, whatever the compute type said.** GDN's chunked
   GEMMs ask for `CUBLAS_COMPUTE_32F` on purpose (design §8.3 / J37: TF32's ~5e-4 mantissa cannot meet the 1e-4 gate),
   and `src/gemm.c` documents the same contract for `JT_EXACT=1`. The shim ignored it, which is the 5.5e-4-6.6e-4 class —
   the rows where the leftover happened to be zero.

Both are needed: fixing only (1) leaves 6e-4, fixing only (2) leaves the leftover-driven 0.14.

## 1. How the two causes were separated without a card

The G-m8probe numbers are reproducible off-card by modelling the same algorithm in C (throwaway program in `/tmp`, nothing
added to the tree; `test/test_gdn.c`'s inputs are synthetic and the seed and generator are in the file, so this is a
faithful replay of the five shapes). Three columns: the chunked WY form with the GEMMs accumulated exactly (fp64
accumulate of fp32 operands), the same with the GEMM *inputs* rounded to TF32 (round-to-nearest, 10 mantissa bits) — what
the shim's `tinyblas_gemm_f32_tc` does — and the same with `T`'s strictly-upper triangle left as leftovers of magnitude
`g`. Reference is the sequential recurrence in fp32, i.e. exactly what the check compares against.

| shape | card B, new cubin | model, TF32 + no leftover | model, exact + no leftover | model, TF32 + leftover `g=0.01` |
|---|---:|---:|---:|---:|
| `B=1 {1}` | 0.000609 | **0.000609** | 4.0e-07 | — (`{1}` cannot see the triangle) |
| `B=1 {2}` | 0.000661 | **0.000661** | 6.3e-07 | 1.8e-04 |
| `B=3 {63,64,65}` | 0.142 | 0.000531 | 1.1e-06 | 4.1e-02 |
| `B=3 {200,7,130}` | 0.000547 | **0.000547** | 1.1e-06 | 4.0e-02 |
| `B=8 {1026,520,670,300,811,455,610,702}` | 0.0742 | 0.000583 | 1.2e-06 | 4.3e-02 |

Three things fall out:

* three of the five card rows are reproduced to three significant figures by TF32 rounding alone — that is defect 2, and
  the agreement at `{1}` and `{2}` in *both* G-m8probe logs (identical digits, different cubins) is why it is not a race;
* the exact-GEMM column is 1e-6 on every shape, which is gpubox's number: defect 1 is invisible wherever the arena starts
  zeroed;
* a leftover of `g=0.01` in `T`'s upper triangle is worth ~0.04 of the output, `g=0.1` ~0.4, and scaling it is linear. So
  the card's 0.142 and the old cubin's 0.423 are two leftover magnitudes run through two GEMM cubins' different rounding —
  no nondeterminism required, and none is available: `{1}`/`{2}`/B=8 are bit-identical across the two logs, which a race
  would not produce.

The `{1}` row is also the cleanest single witness for defect 1: with one token, `X` is zero from row 1 on, so the upper
triangle multiplies zeros and cannot contribute. That is exactly the row that matched TF32 exactly in both logs.

## 2. The fixes

| file | what |
|---|---|
| `train/jeff/kernels/gdn.cu` | `gdn_chunk_trinv_kernel` zeroes its own column's rows above the diagonal (`for (i = 0; i < c; i++) T[i*C + c] = 0`). Fortran-order column ownership means no thread writes another's element, so no barrier and no atomics, and the GEMMs (`Delta = T X`, `dX = T^T dDelta`, `dY = T^T dT`, `dL = -dY T`) can keep taking the whole matrix |
| `train/jeff/test/test_gdn.c` | the chunked arena is prefilled with `0x7f` (a huge finite float) before its first launch, in `case_fwd` (the cross-check) and `case_bwd` (the chunked backward under `JT_GDN_CHUNKED=1`). Scratch, not state: every element the path reads must be written by that call, and this makes a missed write fail on *every* device instead of hiding behind a zeroed allocator |
| `cuda-shim/libtinycublas/cublas.c` | an f32 GEMM takes the TF32 tensor-core kernel only when the compute type is a `*_FAST_*` one **or** the handle's math mode is `CUBLAS_TF32_TENSOR_OP_MATH`; otherwise it takes the exact fp32 scalar kernel. `f32_tf32()` is the single decision, used by `cublasSgemm`, `cublasGemmEx`, `cublasGemmStridedBatchedEx` and the pointer-array variants. f16/bf16 are untouched (their operand mantissa is already at or below TF32's) |
| `cuda-shim/test/cublas_contract.c` | four card-free rows pin that decision (`COMPUTE_32F` + default mode = exact, `COMPUTE_32F` + TF32 math mode = tensor cores, `*_FAST_TF32` = tensor cores, `COMPUTE_32F_PEDANTIC` = exact) through the exported `tinycublas_f32_uses_tf32`, plus one served row that actually launches the exact path |

exact: every exact recipe the scripts have (`ab.sh`, `arm.sh`, `timing.sh`, `parity-steps.sh`, `card-check.sh`) already

(real cuBLAS, always exact), so nothing recorded changes meaning. The behaviour that is new is exactly one case: on the
shim, `COMPUTE_32F` on a handle whose math mode is not TF32 now takes the exact kernel even with the tensor-core path

`JT_GDN_CHUNKED`'s default is untouched (off). Its card record does get slower: the chunked GEMMs now run on the scalar
fp32 kernel on the shim instead of TF32, so variant 5's "+18.5% slower than baseline" becomes worse. That variant was
