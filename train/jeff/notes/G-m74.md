## Why the start mattered, and what it cost

`make_adapter.py` copies the readout from the base checkpoint exactly (as `train.py` does) and draws A from
±1/√fan_in (the same bound `kaiming_uniform_(a=√5)` gives), so the **only** difference between the two starts is
`B`: `N(0,1)·1e-2` versus zeros. That one difference is visible in the first dev check, before any training can hide it:

| step-0 dev soft CE / agreement | |
|---|---:|
| Python arm, both seeds (`train.py`, B = 0) | **1.1299** / 0.6312 |
| this card, B = 0 | **1.1295** / 0.632 |
| the card's earlier arms, `B ~ N(0,1)·1e-2` | 1.1276 / 0.6568 |

With the start aligned, **12 of 15 `score.py` metrics became exactly equal to the Python arm's** — precision, recall,
F1, kind accuracy and `tp`/`fp`/`fn` at both thresholds, several to the last digit (`th0.5.precision 0.879`,
`th0.5.f1 0.935`, `th0.9.precision 0.963`, `th0.9.recall 0.897`, `th0.9.tp 26`, `th0.9.fp 1`, `th0.9.fn 3`). That is
what "the shim trains Jeff the same way gpubox's nvcc+cuBLAS build does" looks like when the two runs start from the
same point — and it is a stronger statement than any of the earlier arms could make.

## The floor

The last metric, `th0.9.maybe_cards`, read **5 vs 7** with the aligned start (and 5 vs 7, 6 vs 8 in the two earlier
arms). Its companions settle what that means: `th0.9.tp 26`, `th0.9.fp 1`, `th0.9.fn 3` are **identical** to the Python
arm, so the two lines in dispute are not cards either implementation misjudges — they are lines both classify the same
way, whose calibrated probability sits within rounding distance of 0.9, landing either side of the boundary after TF32
versus fp32 arithmetic. The band floored counts at 1 line, i.e. it demanded agreement to the last card on a metric whose
own threshold has that much slack; **the user raised the count floor to 2 on 2026-11-10** and the gate closes.

The change is in `scripts/arm.sh` (the header comment records it with its date, the reasoning and the arms that
motivated it, just as it records every other tolerance decision). It does not touch the two CE gates, which are the
design's own numbers and which every arm passes on their own merits: 0.00185 and 0.00370 against 0.01 and 0.02. Both
earlier arms also pass once the floor is 2 (`logs/jefftrain/G-m74-floor2-allarms.log`: seed 0 15/15, seed 1 15/15), so
the floor is the only reason any of the three failed.

## The probe, and the plan's wrong number

A 20-step TF32 probe preceded the arms on the same 20 batches M7.3 timed (same binary, same adapter, only the mode
changed): **1.67 s/step vs exact's 8.94 — 5.34x**; dev check 4 s vs 31 s; 20 steps 53 s vs 278 s. Probe sanity: dev soft
CE 0.77123 (exact 0.77090), loss 1.3240 vs 1.3228 — the TF32-vs-exact spread M7.2 measured.

**M7.4's plan text is wrong and these runs correct it.** It says "at M7.3's 8.94 s/step a full arm is ~9 hours on the
card". 8.94 is the shim's deliberately naive correctness-first fp32 kernel (`libtinycublas/gemm.cu:7`), which exact mode
must use to match Python's true fp32; the arm never runs that kernel — TF32 dispatches to `tinyblas_gemm_f32_tc`
(64×64×32 tiles, shared memory, wmma tensor cores). The measured arm is **1.7 s/step, 1 h 57 min**. Appendix B's
"full-arm s/step not run — at 8.94 s/step it is ~9 h" belongs to the same error and should be replaced by this number.
