## The change (one file, `src/layer_mlp.c`)

Design §4.5 in order, with the call each step uses:

| step | call |
|---|---|
| `dact = dout through down` | `linear_bwd(down)`: `dy = dres`, `dx = dact` (fresh), `dA/dB` for `down_proj` |
| `dh1 = dact * h2 * dsilu(h1)`, `dh2 = dact * silu(h1)` | `k_silu_mul_bwd` over all `n*3584` values, both outputs in one launch |
| `dm = (dh1 through gate) + (dh2 through up)` | `linear_bwd(gate)` into `dm` (`accumulate_dx = 0`), then `linear_bwd(up)` with `accumulate_dx = 1` |
| `dres += RMSNormBackward(dm)` | `rmsnorm_bwd` into a work buffer, then `jt_add_inplace(dres, dnorm, …)` |

`dres` on entry is `dL/d(x_out)`; `layer_fwd`'s `x_out = x_in + y` makes it exactly `down`'s `dy`, and on return `dres` holds
`dL/d(x_in) = dL/d(x_out) + dnorm_backward(dm)` (design §4.6). `gate` and `up` share the input `m`, so their two `dx`'s are
the one place where "accumulate, never overwrite" is load-bearing: the second GEMM's `beta = 1`.

Three decisions worth writing down:

* **The save layout is now one function.** `saves_floats(n)` / `saves_bind(base, n, &acts)` hold the eight arrays of the
  header comment (m, r, u_gate, u_up, h1, h2, act, u_down) and both halves use them: the fwd(SAVE) takes *one* block of
  `11,825` floats per token from the arena's save half and lays it out, the bwd hands the same function `c->arena`. The
  order, the sizes and the count in the header comment therefore cannot drift apart (before this, the fwd took eight
  separate `jt_save_alloc`s and the bwd would have had to mirror them by hand). JT_FWD_ONLY is unchanged in spirit: m, r,
  h1, h2, act from the work half and `u_save == NULL` (linear_fwd's own temporaries).
* **`dact` is the first work allocation and stays readable** at `arena + mark - n*MT_MLP_INTER` for a `mark` taken before
  the call (`jt_work_restore` moves the cursor, not the data; J26's `grad.final` note is the same property). Nothing in a
  bwd is dumped from there today, but M5.2's `--dump-backward` or a future `d(act)` comparison can.
* **The temporaries are given back** (`jt_work_restore`) before returning, so `layer_bwd`'s loop does not grow the arena:
  `dact`, `dh1`, `dh2` [n][3584] and `dm`, `dnorm` [n][1024] = **12,800 floats per token**, against the fwd's 11,825 saves
  — 24,625 of the 98,304 floats per token `JT_ARENA_FLOATS_PER_TOKEN` budgets (25%).
* **Argument checks return `JT_LAYER_FAIL` with a message** naming the function (`bad_args` grew the `fn` argument, so a
  message now says `layer_mlp_fwd` or `layer_mlp_bwd`): null context/weights/x_in/dres, a missing
  `post_attention_layernorm` weight, a missing frozen `W` on any of the three linears, `n < 0`, and a save block bigger
  than the whole arena (which can only mean "was `layer_mlp_fwd` run in SAVE mode?"). `n == 0` is `JT_LAYER_OK`. The
  function does not synchronise the stream.

### A bug this task found and fixed in its own new code

The first version of `saves_floats` counted `r` as `MT_HIDDEN` per token instead of 1, so the fwd(SAVE) block was
`1,023*n` floats too big (12,848 instead of 11,825 per token). Harmless for correctness — `saves_bind` is self-consistent
and the arena is 4x bigger than either — but it made the function disagree with the header comment's own count. Fixed
before the numbers below; the note's 11,825 is the delivered value. The two gates were re-run from a clean build after the
fix (they are bit-identical, as they must be: the layout offsets did not move).

### 1. What the reference holds, and what it does not

`~/macuda-train/ref/ref.safetensors` (403 keys) has, for every layer, the MLP's six `grad.language_model.layers.i.mlp.
{gate,up,down}_proj.lora_A/B` — but **no `grad.layer.{i}.post_mixer` and no `grad.m`**: `py/dump_ref.py` retains
`layer.{i}.out` and `final`, not the MLP's input or the norm's output (`grad.layer.{i}.out` is the MLP's *incoming*
gradient, `layer.{i}.post_mixer` its input). So the parameter gradients are checked against the reference and the MLP's
input gradient (`dm` propagated through the post-attention norm, i.e. `dL/d post_mixer`, the only thing
`layer_mlp_bwd`'s frozen signature hands back) is checked the way plan M5.1 says, by a central difference of the GPU
forward:

```
L(x) = <grad.layer.{i}.out, layer_mlp_fwd(x)>        x = layer.{i}.post_mixer, JT_FWD_ONLY
dL/dx_j = grad.layer.{i}.out[j] + d/dx_j <d0, mlp_path(x)>  ==  what layer_mlp_bwd must leave in dres
```

one element of `x` at a time, `h = 1e-2`, `L` summed in double on the host — the same shape of check as J25's `--fd`, and
per element rather than a random projection. The MLP is per token (design §7), so a per-element FD of `x` exercises the
whole chain: the norm's per-row mean mixes all 1024 columns of a token, `down` mixes all 3584 intermediates, `gate`/`up`
and `k_silu_mul_bwd` sit in between.

### 2. The driver (`test/test_layer.c` is J23's file, and not this task's)

As in notes/J19, J23, J25 and J26: an `--mlp-bwd` mode was written as a **throwaway copy on gpubox only**, never in the
worktree. A Python patch (`/tmp/j27/patch.py`, applied to the gpubox copy; the resulting diff is 219 added lines,
`/tmp/j27/test_layer_j27.diff`) adds the mode and nothing else. It

1. runs `layer_mlp_fwd(SAVE)` from ref's `layer.{i}.post_mixer` and re-checks `layer.{i}.out` at J20's 1e-3 activation gate
   (so the gradient is taken at the model's own activations, not a re-derivation),
2. `lora_zero_grad`, `dres = ref's grad.layer.{i}.out`, then `layer_mlp_bwd(c, lw, x_in, dres, n, b)`,
3. compares the layer's six `grad.{stem}.lora_A/B` against ref at the **5e-3** gradient gate (J26's
   `max|a-b| / max|b|` metric, with the tolerance as a parameter), and checks that **the other 10,223,616 − 6 pairs'
   worth of the LoRA half of the flat gradient buffer are still exactly 0**,
4. reads `dres` back and runs the element-by-element FD above.

### 5. The gate was watched failing twice, and is not h-tuned

Two deliberate bugs, each built on gpubox only and reverted immediately (`md5sum src/layer_mlp.c` back to `8f332d8…`), with
`--fd-limit 2048` to keep them short:

| bug | LoRA grads | dres |
|---|---|---|
| the `up` dm GEMM writes `dm` instead of accumulating (`accumulate_dx = 0`) | all six **ok** (…9.859e-07) | **FAIL rel 5.271e-01** (worst idx 360: fd 0.00953406, got 0.0040939) |
| `dres` left as `d0` (the norm's backward computed, then not added) | all six **ok** | **FAIL rel 5.938e-01** (worst idx 1693: fd 0.00948167, got 0.002702), and the info line reads `dres - d0 0.000e+00` |

That is exactly the signature design §10.2's split predicts: a decision that only affects the *input* gradient cannot be
caught by the parameter gradients, so the reference keys alone would have passed both bugs. (The second one, run on layer
23 first, passed trivially — `rel 0.000e+00` over `--fd-limit 2048`, which is tokens 0–1, whose `d0` is exactly 0. Hence
the full-vector runs above and the note in 3.)

Stability of the FD in exact mode, layer 0, all elements:

```
h 0.003, first 8192 elements   rel 5.734e-05   (noise grows as 1/(2h): more forward rounding, less truncation)
h 0.01 , all 109568 elements   rel 3.618e-05   (the run recorded in 3)
h 0.03 , all 109568 elements   rel 2.967e-04   (truncation grows as h^2)
```

All three are inside 5e-3 by 17x–138x, so the gate is not a choice of `h`. In the **TF32** build (no `JT_EXACT`) the same
2048-element run gives LoRA grads at 5.260e-04 (still passing) but `dres` **FAIL at rel 1.512e-02**: the FD divides the
forward's TF32 noise by `2h`, so the FD *gate* only exists in exact mode — design §10.2's rule, and the same conclusion
J25 reached for a different reason.

## Numbers worth recording for the later tasks

* **Cost.** At the plan's batch (N = 4200) the MLP's backward is three `linear_bwd`s ≈ 32 GFLOP each (J25's count: `dg`'s
  `e`+`dx`+`dx+=eA`+`dB`+`dA`), i.e. **≈ 96 GFLOP against the forward's ≈ 92 GFLOP** (three 4200×3584×1024 projections), so
  a layer's MLP step is ~2x its forward and design §15's "a training step is ~2x the forward" holds inside the MLP alone.
  The elementwise work is `k_silu_mul_bwd` over 15.05 M values plus one `rmsnorm_bwd` over 4200 × 1024.
* **Arena.** Saves 11,825 + temporaries 12,800 = **24,625 floats per token** (98.5 KB), 25% of
  `JT_ARENA_FLOATS_PER_TOKEN`. At the fixture (n = 107) that is 2.63 M floats (10.5 MB); at B = 8 / N = 4200 it is
  103.4 M floats (414 MB), all inside the arena `jt_ctx_alloc` already sizes (0.04 GB printed for the fixture).
* **For M5.2 (`--dump-backward`) and M5.4.** `layer_mlp_bwd` writes only the six parameter gradients and `dres`; its
  trailing means the layer loop can call `layer_fwd(SAVE)` → `layer_bwd` per layer with no accumulation buffer of its own
  and no arena growth. The pieces must run in the order `head_bwd` → `layer_bwd(23)` … `layer_bwd(0)`, and the MLP's
  `dres` output is layer i−1's mixer input gradient. `dact` is readable at `arena + mark - n*3584` after the call if a dump
  ever wants it.
* **The two kinds of `dres`.** `grad.layer.23.out` is supported on 2 of 107 rows and so is layer 23's `dres`; layer 0's is
  dense. Any future per-layer gradient check should keep one dense layer in its set (J25's finding, confirmed here: a
  2048-element FD window of layer 23 is all zeros).
* **Cross-check available for free.** `test_linear --layer i` (J25's, in the tree) reproduces the same six numbers by
  hand-rolling the chain around `linear_bwd` — it is the reference for this function's order, and it still passes.
