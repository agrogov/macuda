## The change (one file, `src/layer_mlp.c`)

```
m    = RMSNorm(x_in; post_attention_layernorm)   rmsnorm_fwd(..., d = 1024, zero_centred = 1)   r saved
h1   = gate(m)                                   linear_fwd(lw->gate, m, n, h1, u_gate)          LoRA
h2   = up(m)                                     linear_fwd(lw->up,   m, n, h2, u_up)            LoRA
act  = silu(h1) * h2                             k_silu_mul_fwd(h1, h2, act, n * 3584)
y    = down(act)                                 linear_fwd(lw->down, act, n, y, u_down)         LoRA, into a work temp
x_out= x_in + y                                  memcpy (only when x_out != x_in) + jt_add_inplace
```

i.e. design §3.4's last two lines and D§4.5, using only kernels that already exist and are tested; this file is their
order, their buffers and their sizes. Four decisions the frozen contract forced, all recorded in the file's header:

* **The saves (JT_FWD_SAVE), in the fixed order a bwd can replay them from the bump allocator.** 1 `m` [n][1024],
  2 `r` [n], 3 `u_gate` [n][16], 4 `u_up` [n][16], 5 `h1` [n][3584], 6 `h2` [n][3584], 7 `act` [n][3584],
  8 `u_down` [n][16]: **11,825 floats per token**, against `JT_ARENA_FLOATS_PER_TOKEN` = 98,304. `layer_mlp_bwd`'s owner
  reads them in that order (the order is checked, see the numbers below).
* **JT_FWD_ONLY keeps nothing** (design §6.2's recompute pass): `m`, `r`, `h1`, `h2` and `act` come from the arena's work
  half and are given back with `jt_work_restore` before returning; the three `u`s are `linear_fwd`'s own work temporaries
  (`u_save == NULL`, src/linear.c). Checked: the save cursor is unchanged after an ONLY pass.
* **The residual and aliasing.** `x_out` may alias `x_in` (src/layer.h; `layer_fwd` passes one buffer for both in a
  JT_FWD_ONLY pass), so `x_in` is read exactly once — by the input norm — before anything writes `x_out`. `down` writes a
  work temporary `y` [n][1024] and the residual is `x_out = x_in` (a D2D `cudaMemcpyAsync` on `ctx->stream`, skipped when
  they are the same pointer) then `x_out += y` (`jt_add_inplace`). No GEMM ever writes an output that still holds an
  input, and nothing else aliases.
* **Bad calls return `JT_LAYER_FAIL` with a message naming the tensor** (`stem`, design §9.2): null arguments, a mode that
  is neither `JT_FWD_ONLY` nor `JT_FWD_SAVE`, a missing `post_attention_layernorm` weight, an MLP linear without `W`,
  negative `n`. `n == 0` is `JT_LAYER_OK` with no work. Nothing here returns `JT_LAYER_NOT_IMPL` except the bwd stub.
* The batch's row table `b` is deliberately unread: the MLP is a per-token op (design §7), so no row boundary can matter.

## Numbers worth recording for the later tasks

* The forward is one RMSNorm + 3 linears (3 GEMMs each, 9 in total with LoRA) + one elementwise pass + the residual's two
  elementwise passes. At the plan's 8 x 525 batch (N = 4200): gate 4200x3584x1024x2 = 30.8 GFLOP, up the same, down the
  same, plus 3 x 0.62 GFLOP of rank-16 pairs — about 94 GFLOP per MLP per layer, i.e. about 94 x 24 = 2.3 TFLOP per
  whole forward (a training step is roughly twice that). The recurrence and attention layers are a small fraction of it,
  so the MLP dominates the bill.
* Arena: 11,825 saved floats/token (47 KB/token, 199 MB at N = 4200 in a SAVE pass) and 12,801 work floats/token in an
  ONLY pass. Both are far inside the 98,304 floats/token budget, so nothing in `JT_ARENA_FLOATS_PER_TOKEN` has to change
  for this piece.
* Error budget: this piece's own error against the double-accumulating fp32 oracle is <= 6.6e-07 relative, three orders
  under design §10.2's 1e-3 gate, so M4.4's whole-forward comparison has room to absorb the mixer's error.
* For M5.1 item 3 (`layer_mlp_bwd`): the save order is the one in the file's header (m, r, u_gate, u_up, h1, h2, act,
  u_down), 11,825 floats/token; `x_in` passed to the bwd is the post-mixer residual (`layer_bwd` passes `post_mixer`),
  and `dres` on entry holds dL/d(layer.i.out).
