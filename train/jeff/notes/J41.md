## The M6.4 cost correction (the task's explicit item)

`plan M6.4` said "one arm, about 30 min". G-m63's measurement (1.061 s/step at batch 8) and G-m64's arithmetic put it at
**~74 min**, and the plan now carries the table instead of the estimate:

| piece | count | unit | total |
|---|---:|---|---:|
| optimizer steps (28,645 rows / batch 8) | 3,581 | 1.061 s/step | 3,799 s = 63.3 min |
| dev checks (all 1,722 dev rows, step 0 + every 500 + epoch end) | 9 | 61 s | 549 s = 9.2 min |
| calibration (1,679 rows) + test (160 rows) evals, T=1 | 2 | ~60 s + ~6 s | 66 s = 1.1 min |
| rebuild + adapter | 1 | ~41 s | 0.7 min |
| | | | **4,455 s = 74.3 min** |

The plan also now records that a full arm is 10–13% slower per step than the 100-step timing run (1.202 and 1.164 s/step,
because the dev checks leave the card cold), so the honest window is 75–85 min; that the measured runs were 75.5 and
76 min; that the first attempt was refused a **60-minute** card on exactly this arithmetic (`logs/jefftrain/G-m64-rerun.md`)
and the two that succeeded ran under a raised **90-minute** cap; and that the training loop alone (63.3 min) is already
over an hour, so an hour is not a workable cap for this checkpoint.
