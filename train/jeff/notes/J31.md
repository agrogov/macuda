## What is implemented

* `main()`: one optimizer step is plan M5.2's list in its order — `lora_zero_grad`, then for every batch of the
  accumulation group (`Wgroup` = the group's summed row weight) upload, `model_forward` (saving each layer's input),
  `head_fwd(SAVE)` with `wgroup`, `head_bwd` → `dres`, `model_backward` (the design §6.2 recompute sweep); then the global
  norm (`k_sumsq_partial`/`k_sumsq_final` → **sqrt**), the clip to 1.0, `lr_at(step,total,1)` on both groups and
  `k_adamw_step` with `t = step+1`'s bias corrections; `step += 1`.
* Log lines are train.py's, character for character (`  step N/T  X.XXs  loss …  … rows/s  peak … GB  lr …` and
  `  dev @ step N: soft CE …  agree …[  *saved]  (Ns)`), so `tools/jeff_lora/cuda/timing.sh` parses them as is. `loss` is
  the running mean of the **unweighted** per-row CE since the last dev check (train.py's `run_loss/run_n`); `lr` is
  `--lr * lambda(step)` — `sched.get_last_lr()` is read after `sched.step()` in train.py, so the logged value is the next
  step's; `peak` is `cudaMemGetInfo` total−free, the maximum seen.
* Flags: every one in plan M5.2 (`--model --train --dev --eval NAME=PATH --output --lr --readout-lr --epochs --batch
  --accum --eval-every --max-steps --eval-temperature --eval-only --init-adapter --log-every --dump-forward
  --dump-backward`) plus `--trace-loss FILE` (M6.2 needs it), `--targets`, `--weights`, `--weight-cap` (recorded in
  report.json/adapter_config.json; only prep.py acts on them). `--log-every` default is train.py's rule (steps 1–3, then
  every 25th).
* The dev check, the best-adapter save and reload, and `--eval` follow train.py's `check()`/`evaluate()`: dev is scored
  with `batch*2` rows per batch, `--eval` with `max(2, batch*2)`, no shuffle (prep.py wrote those batch lists); the
  selection metric is the teacher's soft CE at T=1; the evals run after the best adapter is reloaded; agreement is
  `argmax(logits) == teacher_top`; `pred-<name>.jsonl` is one line per row in input (row-index) order with
  `softmax(logits/T)` over the row's live options rounded to 6 decimals, keyed by the row's criteria keys.
* `report.json` has train.py's keys: `args`, `model`, `device`, `eval_temperature`, `row_weights` (null: prep.py owns
  them), `history` (step/rows_seen/tag/dev_soft_ce/dev_agreement/train_loss/seconds/peak_gb/saved), `train_seconds`,
  `rows_per_second`, `steps`, `best_dev_soft_ce`, `eval_<name>` {n, soft_ce, teacher_argmax_agreement, seconds}, `peak_gb`.
* Flag/`.jtb` disagreement is rejected (see the note below about where batch/accum/epochs live).
* `--trace-loss`: one JSON line per step, `{"step":k,"row":[row indices],"ce":[per-row soft CE]}`, in batch order (the
  group's batches in file order, each batch's rows in file order). The per-row CE is computed on the host from the step's
  fp32 logits and the row's targets (double `-Σ t·log softmax`), because `head_fwd` only hands back the weighted batch
  sum and both the log line and the trace want per-row values.

## The optimizer step, checked numerically (this found a bug)

Design §2.2 assigns step parity to M6.2, and M6 tasks may not edit `main.c`, so the step was checked here instead:

1. `JT_EXACT=1 … --init-adapter ~/macuda-train/ref/adapter --train F.jtb --dump-backward g0.safetensors` gives the batch's
   gradients at θ0 (F.jtb = `make_fixture --seed 11 --rows 2 --lengths 37,70 --opts 5,12 --batch 2`, 1 batch).
2. `… --train F2.jtb --dev D.jtb --batch 2 --epochs 2 --lr 8e-6 --readout-lr 8e-6 --max-steps 2` (F2.jtb = F.jtb's batch
   twice, so step 2 re-uses the same rows); the step-1 dev check improved, so the step-1 adapter is on disk.
3. A Python reimplementation of design §2.2 (clip `coef = 1/(sqrt(Σg²)+1e-6)`, `m=(1-b1)g`, `v=(1-b2)g²`,
   `p -= lr·(m/bias1)/(sqrt(v/bias2)+eps)`, t=1, lr group split at the readout) applied to θ0 and `g0`:
   `grad norm 20.855596 -> clip coef 0.047949 (applied)`, `max |python Adam step − jefftrain's step-1 adapter| = 3.7e-09`
   over all 301 tensors.
4. Step 2's traced per-row CE is bit-identical to the CE from a `--dump-forward` run started from the saved step-1
   adapter (same batch): `[1.755749845115, 2.62912076263]` = `[1.755749845115, 2.62912076263]` — so the update lands in
   the master parameters and the next step's forward reads it.

The first version of this check failed with `5.1e-06` because `k_sumsq_partial`/`k_sumsq_final` return the **sum of
squares** and the host must take the `sqrt` (`ref_clip_coef(sqrtf(sq))`, test/k_adam.c:138). Without it the clip used
435 instead of 20.86 and was ~21× too strong. Fixed in `optimizer_step`; the check above is the regression test for it.
(`--lr 0 --readout-lr 0` leaves the adapter bit-identical, and the dev CE moves monotonically with lr: 1.1961 at 0,
1.2018 at 8e-6, 1.2452 at 4e-5, 1.9317 at 2e-4, 7.03 at 1e-3 on a 3-row synthetic dev split — the sharp growth is the
synthetic set's near-uniform logits and argmax flips, not a scaling bug.)

## Notes for later tasks

* **`--trace-loss` format** (M6.2's `compare_steps.py`): JSON lines, one per optimizer step, keys `step` (1-based), `row`
  (the `.jtb`'s row indices, batch order), `ce` (per-row unweighted soft CE, float64 printed with `%.15g`). With
  `--accum k` one record covers the whole group (`k` batches' rows).
* **Where batch/accum/epochs live.** Design §9.1's `.jtb` header has no room for them (it is
  `n_rows/n_batches/max_tokens_per_batch/max_len/max_opts` + the section table), so the check is structural:
  `n_batches == ceil(n_rows/batch) * epochs` and every batch's row count must equal
  `min(batch, n_rows − (k mod per_epoch)·batch)` — that rejects a wrong `--batch` and `--epochs`. `--accum` cannot be seen
  in the `.jtb`; when py/prep.py's `<split>.prep.json` sidecar exists (plan M5.3) its `batch`/`accum`/`epochs`/
  `eval_batch`/`targets`/`weights`/`weight_cap` are checked too, and `--targets`/`--weights` are adopted from it when the
  run does not name them. The fixtures have no sidecar, so their structural check is the only one.
* **Memory.** One `JtCtx` serves the whole run, sized from the largest batch of any split — and the dev/eval splits batch
  `batch*2` rows, so `cap_tokens` is roughly twice the train split's `max_tokens_per_batch` (arena =
  `cap_tokens·98304` floats, plus 25 saved-input slabs `[cap_tokens,1024]`). gpubox is a 32 GB RTX 5090, so M6's
  `--batch 8` is fine there; on a 12 GB card use `--batch 4` (design §14's fallback). Splits a run does not score should
  not be passed with a dump: `--eval` is ignored when `--dump-*` is given.
* **Per-step host pulls.** Each training batch pulls its `[B][n_opts]` logits so the log line and the trace can have
  per-row CE; that costs one stream sync per batch (included in the logged `X.XXs`). A later M8 change could fold it into
  ce_head's reduction without changing any number here.
* **`--eval-every 1` prints the last step's dev line twice** when the run also ends there — that is train.py's own
  behaviour (its `if not a.eval_every or done:` runs after the `break`), with tags `step` and `epoch N` in the history.
* No card run: M5.4 is the separate card checkpoint (`sh scripts/card-check.sh <A|B> m5`) and needs the user's OK.
* gpubox numbers for the record: 8-row fixture, 2 steps — 0.09 s/step, 15.6→23.1 rows/s, peak 4.82 GB (2.5 GB of that is
  the fp32 weights + bf16 embedding), dev soft CE 1.2129 → 1.2132, eval (5 rows) soft CE 1.6199, agreement 0/5.
