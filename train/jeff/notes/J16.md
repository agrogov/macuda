```
ptxas info    : Compile time = 34.362 ms
```

**201 registers, 0 spill stores, 0 spill loads, 1024 bytes of smem** (two 128-float warp-shared arrays), recorded in the
`kernels/gdn.cu` header comment as the plan asks. 201 * 32 = 6432 of an SM's 65536 registers, so 10 blocks (10 warps) per
SM.

That zero was not free; it is the one place where the kernel departs from a literal reading of design §8.3, and the
numbers that decided it (each measured with the command above, same flags):

| kernel body | registers | spill stores / loads |
|---|---|---|
| one `#pragma unroll` loop of 128 for the decay + kv sum, one for the write + o | 255 | 68 B / 52 B |
| the same with the 128-iteration stores written through a base pointer + `int` index | 255 | 68 B / 52 B |
| **each 128-iteration loop split into two 64-iteration halves, `__syncwarp()` between** | **201** | **0 / 0** |
| four 32-iteration chunks instead of two 64s | 203 | 0 / 0 |

With one unrolled block ptxas prefetches all 128 shared loads of the sum, runs into the 255-register ceiling and spills.
A `__syncwarp()` between the halves is a scheduling barrier it cannot move loads across, and since it sits in the loop
body every one of the warp's 32 lanes reaches it (the tile, head, row and `ckpt != NULL` predicates are warp-uniform), so
it costs nothing but the instruction. The sums still run i = 0, 1, … 127 ascending — same arithmetic, same order as one
loop, so the numbers are unchanged. Two comments in the file say this; `test/test_gdn.c`'s `no_ckpt_identical` check ties
the two halves together numerically.

## What the kernel is (and the two decisions the plan left open)

`gdn_fwd_kernel`: grid `(B, H, 4)`, block 32, lane l owns value column j = tile*32 + l and holds `float s[128]` — that
column of S — in registers for the whole row. Per token: the warp stages `k[t,h,:]` and `q[t,h,:]` in shared memory
(4 entries per lane, `__syncwarp()`), `e = expf(g[t,h])`, `for i: s[i] *= e; kv += s[i]*k_s[i]`, `d = (v - kv)*beta`,
`for i: s[i] += k_s[i]*d; acc += s[i]*q_s[i]`, `o[t,h,j] = acc`. No cross-lane reduction anywhere: design §3.6's columns
are independent, which is the whole point of the shape. S starts at 0 at each row's first token (rows of a packed batch
share nothing, design §7), and `off` is a **device** pointer, like `conv.cu`'s row table — the trainer builds it there.

Two things the plan/design left open, decided here and written down in `kernels/gdn.h`:

1. **Who owns the checkpoint buffer.** The caller: `gdn_fwd(..., int nseg, float *ckpt, float *o, cudaStream_t s)`, with
   `ckpt` laid out `[B][H][nseg][128][128]` (design §8.3), `nseg = gdn_ckpt_segs(off_host, B)` = ceil(longest row / 64)
   and the size `gdn_ckpt_floats(B, H, nseg)` — both `static inline` in the header, so `layer_gdn.c` and J17 share one
   definition. Caller-owned because the forward and the backward are separate calls and the buffer must outlive the first
   (plan M3.3: supporting buffers "allocated once by the caller"); there is no global scratch (plan rule 8). `ckpt` may
   be NULL (o only) and `nseg <= 0` is treated as NULL, so a forward-only pass costs no memory and no stores.
2. **When the checkpoints are written.** Before the token's step, exactly as design §8.3 says, so the slot for segment 0
   is all zeros for every (row, head). A row shorter than 64 tokens writes only that slot; a 1026-token row writes 17.

At B = 8 / N = 5094 the checkpoints are 142.6 MB (8 * 16 * 17 * 64 KB) and cost nothing measurable: 1.26 ms with them,
1.25–1.33 ms without (run-to-run noise is larger than the difference). Per the plan's M3.3/M3.4 budget note this is the
**forward's** share of the ~2 ms *fwd + bwd* per layer the design hopes for, so J17's backward is where that number gets
tested.

## What `test/test_gdn.c` checks (three properties beyond the numbers)

* `gdn_fwd <batch>` — o against `ref_gdn_fwd`, gate 1e-4 (`TOL` in the file, the plan's number for this kernel; not the
  plain forward's 1e-5, since a 1026-token recurrence is not a 128-term sum).
* `gdn_fwd_no_ckpt_identical` — a second launch into another buffer with `ckpt = NULL` must reproduce the first **bit for
  bit** (err = 0 exactly). The checkpoints are stores; if they perturbed the arithmetic, that would be a bug.
* `gdn_fwd_ckpt0_zero` — segment 0 of every (row, head) is exactly zero. The whole buffer is prefilled with `0x7f` bytes
  (`cudaMemset`) before the launch, so this also proves the kernel wrote it, and `gdn_fwd` matching the oracle proves the
  forward never *reads* it.
* `gdn_fwd_ckpt_replay b=… h=… seg=…` — the last segment of the last row is replayed on the host in double from the
  kernel's own 64-KB checkpoint slice and must reproduce the o the kernel wrote for those tokens (gate 1e-4). This is the
  check on the *moment* the checkpoint is written: a checkpoint taken after the step instead of before it is caught.

Cheap is deliberate: the whole `fwd` binary is 2.3 s, of which ~2 s is `ref_gdn_fwd` (J13 measured 1.83 s at N = 5094).

Three mutations confirm the group is not vacuous (throwaway copies of the tree under `/tmp/mut` on gpubox, the repo never
mutated; each run is `make build/nv/test_gdn && ./build/nv/test_gdn fwd`):

| mutation | caught by | where it shows |
|---|---|---|
| o read from the decayed S (`Sd`) instead of `S_t` | `gdn_fwd` + `ckpt_replay`, all five batches | rel 0.80–1.0 |
| checkpoint written *after* the step instead of before | `ckpt0_zero` (all batches) + `ckpt_replay` | err 0.076–0.087, rel 0.43–0.45 |
| `delta` without the `* beta` | `gdn_fwd` + `ckpt_replay` | rel 0.84–1.25 |

(`gdn_fwd_no_ckpt_identical` survives all three, by construction: it compares the kernel against itself.) The second row
is the interesting one — the o comparison alone does *not* see a mis-timed checkpoint, which is why the replay check
exists.

## Notes for J17 (plan M3.3, the backward — same three files)

* Use `gdn_ckpt_segs()` / `gdn_ckpt_floats()` from `kernels/gdn.h` to size the forward's `ckpt`; `gdn_fwd` writes it
  already, segment 0 all zeros, one segment per 64 row-local tokens. `test_gdn fwd`'s `ckpt_replay` check proves the
  contents and the timing at the three boundary cases ({63,64,65}, {200,7,130}) — reuse the same batches for phase A.
* J13's note stands: `ref_gdn_bwd` keeps its own checkpoints internally and does not expose them, so plan M3.3 step 1's
  "compare `sp` for segment 0 with the ref's stored S_prev" cannot be done against `ref_gdn_bwd` directly. The honest
  form is a kernel-vs-kernel check (the replay `test_gdn.c` already does for o proves the checkpoint is the right state),
  or ask for the buffer to be exposed.
* Register discipline transfers: the split-half trick above is what turned 255 registers + spills into 201 + zero at
  *this* loop structure; the backward's per-token loops will hit the same ceiling sooner (two 64-float arrays), which is
  why plan M3.3's budget note says to read `sp` back from scratch rather than keep `sp[64]`/`st[64]` live.
* `test_gdn.c` is already a dispatcher (`PARTS[] = {{"fwd",…},{"bwd",…}}`): replace `group_bwd`'s stub body and nothing
  else needs touching. The batches, `TOL`, `H`/`D`, `xalloc` and the exit-code contract are shared.
* Numbers to plan against: fwd is **1.26 ms** at B = 8 / N = 5094 (one layer, card clock) and the fwd's 142.6 MB of
  checkpoints cost nothing measurable (1.25–1.33 ms without them, i.e. inside the noise); the design's ~2 ms per layer for
  fwd + bwd therefore leaves J17 about 0.7 ms before it has to explain itself.
