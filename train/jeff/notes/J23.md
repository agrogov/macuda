## The change (one file, `src/head.c`)

The forward, in design §4.1's order, with the call each step uses:

| step | call |
|---|---|
| `final = RMSNorm(x; norm)`, d = 1024, zero-centred (`1 + w`) | `rmsnorm_fwd` (kernels/norm.h), `r` requested |
| `z[b] = final[off[b+1]-1]` | one `cudaMemcpyAsync` (D2D, on `ctx->stream`) per row: B copies of 4 KB, no gather kernel |
| `logits = z R^T`, first `n_opts` readout rows | `gemm(0, 1)` M = B, N = n_opts, K = 1024, `R = ctx->lora->param + readout_off` |
| `logits[b][j >= live[b]] = -1e9` | one `jt_fill` per row (`-1e9f`, on `ctx->stream`), a no-op for a full row |
| loss, dlogits, probs | `ce_head` (kernels/head.h) with `probs_out = NULL` |
| `*loss = sum_r loss_out[r]` | one D2H copy of the B per-row losses + one `cudaStreamSynchronize` |

The readout GEMM is the design's `gemm(0,1)` against the readout in the flat parameter buffer: `z` is the `A` argument
stored [M,K] = [B,1024] and `R` the `B` argument stored [N,K] = [n_opts,1024] (torch's `[out, in]` rows), so the
slice `[:, :n_opts]` of `train.py` is the GEMM's N — no copy, no transposed weight, and the dead columns are never
computed and then overwritten with `-1e9`.

Four decisions the frozen interface forced, all written down in the file's header comment:

* **The save layout (for M5.1's `head_bwd`).** `head_bwd`'s frozen signature is `(c, x, n, b, dres)` — it carries no
  `HeadBatch`, so it cannot be told `n_opts`. In `JT_FWD_SAVE` mode the saves are therefore taken from the arena's save
  half in the fixed order `r [n]`, `z [B][MT_HIDDEN]`, `dlogits [B][MT_READOUT_OUT]`, where the dlogits are **zero-padded
  to the readout's 255 columns**. The padding is not a second approximation: a dead column's `dlogits` is exactly 0
  (`p = 0` and `t = 0`), so the padded array is the same gradient as the `[B][n_opts]` one, and `dz = R^T dlogits` over
  all 255 rows adds nothing from them. `jt_zero` then one `cudaMemcpyAsync` per row (2 KB of save, 8 tiny copies at the
  plan's B = 8). This is stated in `src/head.c` again where `head_bwd` will be written.
* **`head_fwd` is the one layer call that synchronises.** It reads the loss back to the host, as `src/layer.h` says
  ("this is the one function that synchronises the stream to read it"). With `loss == NULL` it never synchronises and
  the logits stay device-side, which is what an evaluation and a `JT_FWD_ONLY` pass want. The host sum is in double, so
  the only rounding is `ce_head`'s own.
* **"logits only" is `targets == NULL`.** `src/layer.h` allows `targets`/`wrow` to be NULL; they arrive together
  (`collate`'s output) or not at all, and asking for a `loss` without targets is a `JT_LAYER_FAIL` with a message, not
  a silent 0.
* **`final` is optional and is the norm's own output.** When the caller passes it (dump_ref's `final` key, and
  `test_layer --head`), `rmsnorm_fwd` writes it directly — no copy. When it is NULL the norm output comes from the
  arena's work half, which is what a training step will do; measured below to give bit-identical logits.
* **Argument checks return `JT_LAYER_FAIL` (never `exit()`), like `linear_fwd`:** null context/model/parameter
  buffer/x/b/hb/logits, `b->rows` outside `0..JT_MAX_ROWS`, `b->off[rows] != n`, `n_opts` outside
  `1..MT_READOUT_OUT` (255), a missing `hb->live`, a `live[r]` outside `0..n_opts`, an unknown `mode`, a missing
  `wgroup` with targets, and a readout offset outside the flat buffer. An empty batch (`B == 0` or `n == 0`) is
  `JT_LAYER_OK` with no work.

`head_bwd` is **not** written here (plan M5.1 item 1 is its task): it is still plan J18's stub, printing
`head: head_bwd: not implemented (plan M5.1)` and returning `JT_LAYER_NOT_IMPL`, with the save layout it will read
recorded above it.

### 2. The logits gate is weaker than it looks, so it was measured properly

`test_layer`'s metric is design §10.2's `max|a-b| / max(|b|)`, and this reference's `max(|b|)` is the `-1e9` of the two
dead columns — so `rel = 9.537e-16` above only says the dead columns hold exactly `-1e9`. To get a number that gates the
*readout*, a **throwaway copy** of `test/test_layer.c` (in the gpubox directory only, never in the worktree, deleted
before the clean build of 3, the plan-rule-5 pattern notes/J19.md used) skipped the dead columns in the metric and
counted them separately:

```
final  rel 1.325e-07  ok  |  live-only rel 1.325e-07  (all-values rel 1.325e-07)  dead 0,  dead not -1e9 0
logits rel 1.729e-07  ok  |  live-only rel 1.729e-07  (all-values rel 9.537e-16)  dead 2,  dead not -1e9 0
loss   rel 1.678e-07  ok  (got 1.42077231, ref 1.42077208)
```

So the five live logits agree with the CPU oracle to **1.729e-07 relative** (the same order as `final`'s 1.325e-07 over
109,568 values, and as M4.3 item 1's `linear_fwd` gate), and both dead entries are **exactly `-1e9f`**, as
`train.py`'s `masked_fill(~live, -1e9)` writes them. The same copy also ran the head a second time with `final == NULL`
and `loss == NULL` (the training step's shape — the norm output as a work temporary):

```
head_fwd(final=NULL, no loss) rc 0, max|logits - logits(final)| 0.000e+00 over 10 values
```

i.e. bit-identical, so the arena temporary is not a second arithmetic path.

The 1e-3 gate is not reachable by accident: the same binary without `JT_EXACT` (`gemm: tf32`) gives

```
final  rel 1.325e-07   logits rel 5.121e-13 (all-values; the -1e9 columns)   loss rel 2.047e-05
```

— still passing, but the loss moves by 2.0e-05 relative in TF32, which is why design §10.2 asks for `JT_EXACT` at this
gate and why the number above was taken in the exact build.

## Numbers worth recording for the later tasks

* The head is **2 kernel launches + B gathers + B fills + 1 GEMM** on the forward, and 4 extra D2D copies of 2 KB each
  in SAVE mode (the dlogits padding). At the plan's batch (B = 8, N = 4200 tokens) the GEMM is 8 x 255 x 1024 x 2 =
  4.2 MFLOP — nothing next to one layer's 30.8 GFLOP projections. The save cost is 4200 + 8 x 1024 + 8 x 255 =
  **14,432 floats (56 KB)**, so the head never comes near design §6.2's arena budget.
* `final` for the 2-row fixture is 107 x 1024 values at rel 1.325e-07; that is the norm kernel's own error against the
  CPU double-accumulating oracle, so a later whole-forward failure of more than about 1e-6 on `final` is not the head's
  norm.
* `loss` reproduces `train.py`'s `(per * wt).sum() / gw` decomposition exactly: `ce_head`'s per-row loss already carries
  `wrow[r] / wgroup` (here `gw = 2`, the fixture's two weights of 1), and `head_fwd` only sums. Row 0's target is
  "soft" (`|sum(t) - 1| <= 1e-4`), and `ce_head`'s `p * sum(t) - t` form of the gradient is what M5.1's `dlogits`
  should stay consistent with.
* For **M5.1**: the save layout is `r [n]`, `z [B][MT_HIDDEN]`, `dlogits [B][MT_READOUT_OUT]` (zero-padded), in that
  order from `arena[0]`; `head_fwd(SAVE)` allocates them in exactly that order, so a `head_bwd` can index them from the
  arena base. `test_layer --head` calls `head_fwd(..., JT_FWD_SAVE)` and recomputes the saves on every run, so a
  backward test can follow the same pattern.
* For **M5.2/M6**: `head_fwd` returns the loss as a **float host value** (`*loss`), not device-side; a step that wants a
  device-side loss graph does not exist here (the step reads the loss for its log and schedule, as `train.py` does).
