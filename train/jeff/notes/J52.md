# J52 — the store's MMU fault: GdnBwd.dy was budgeted at the hidden size, not at the gated norm's width

G-m8probe filed this as its own card: **batch 4 x accum 2 with `JT_NO_RECOMPUTE=1` faults the card**, 3 of 3 runs, after
the step-0 dev check, `mmu fault on the compute channel ... no page directory entry (write)` at `0x1592e01000`, then
`CUDA error 999` in `cudaFree` (`src/model.c:437`); the same toggle worked on gpubox with a 22.94 GB store (J39). The
cause is in `src/layer_gdn.c`, one allocation width, and it is a latent bug in the *recompute* path too — the store only
made it visible by putting the buffer at the very end of the allocation.

First command run, before anything else (plan rule 9):

```
$ sh train/jeff/scripts/prereq-check.sh J39 J50
prereq: J39 J50 PASS
```

## The cause, in one paragraph

`layer_gdn_mixer_bwd` takes its `dL/d(y)` buffer (`GdnBwd.dy`) as `take(c, 0, MT_HIDDEN, n)` — 1,024 floats per packed
token — but that buffer is `out_proj`'s **dx**, i.e. the gradient with respect to the gated norm's output, whose width is
`GDN_W` = **2,048**. The two GEMMs that write it (`dx = dy W` and `dx += e A`) therefore write a full `[n][2048]` block
into a `[n][1024]` buffer: exactly one extra `[n][1024]` slab past its end, contiguous. On the recompute path that slab
lands on the MLP backward's scratch, which the mixer's backward has already finished with, and the `gated_rmsnorm_bwd`
that reads `dy` reads back *the same region the GEMMs just wrote* — so the numbers were right and nothing ever showed. On
`JT_NO_RECOMPUTE` the first work allocation of a piece is the top of the store's shared work region, so `dy`'s slab ends
at the last word the store owns and the extra slab leaves the allocation.

The fix is that one line (`kw`, not `MT_HIDDEN`) plus the comment that says why. `src/layer_gdn.c` +6/−2; nothing else in
the trainer changed except the diagnostic below.

## How it was found (the fault named nothing, so the diagnostics had to)

1. **What the address was.** The faulting range is the single `cudaMalloc` holding arena + store (`#44`,
   15,348,042,560 B = 2,403,045,376 arena + 12,944,997,184 store). The driver maps `request + 64 KB`, rounded up to 2 MB
   (`libtinynv/src/tinynv.c`'s slack, `pt.c`'s big-page rounding), i.e. 15,349,055,488 B, so there is 1,012,928 B of
   padding after the request and the fault sat one page past the *mapped* end.
2. **Which phase.** Replayed the run's launch sequence on the **null device** (same `.jtb`, adapter and arguments). Card
   vs null per-kernel counts are exactly 2:1 for every kernel (`tinyblas_gemm_f32_tc` 6107 vs 12214, `gdn_fwd` 162 vs
   324, `attn_softmax_bwd` 24 vs 48, ...), so the card stopped exactly halfway through step 1: the dev check (9,624
   launches) plus one micro-batch's forward and backward (2,523 of 5,049).
3. **Whether it was the allocation or the mapping.** Two knobs, two runs: `TINYNV_ALLOC_SLACK_KB=4096` (the request
   unchanged, the mapping 4 MB bigger) and `JT_NO_RECOMPUTE_GUARD=4096` (the allocation 4 MB bigger) both moved the fault
   from `0x1592e01000` to `0x1593201000` — the mapped end in each case. So the write ran off the *mapping*: not a stray
   pointer, but a write that starts inside the arena and keeps going.
4. **Which piece.** A guard above the work region (`JT_NO_RECOMPUTE_GUARD=<KB>`: poison, then check it after every piece)
   caught it at `layer 22's mixer backward`, `first byte +0, span 7835648` — 7,835,648 B = 1,958,912 floats = `1024 n`
   with n = 1,913 (the prep's first train batch), starting at the store's top.
5. **Which step of the piece.** A temporary probe between the mixer backward's steps (removed again) named
   `out_proj (linear_bwd)`, and `TINYCUDART_TRACE=1` showed the launch: `tinyblas_gemm_f32_tc grid=(32,30,1) m=2048
   n=1913 k=1024` — cuBLAS `m` = 2,048 (= `out_proj.in`), while `C` is `g.dy`, `[1913][1024]`.

Everything before step 4 was also done with new driver diagnostics (kept, they are what a fault report should have said
anyway): the stall report now names the **kernel** of the oldest unfinished batch, a detected fault prints the last
launches with their **parameters** checked against the VA ledger (`NOT IN ANY ALLOCATION` for a pointer the driver got
wrong, a pointer *inside* one meaning the kernel indexed out of it), and an MMU fault prints the faulting **warp pc** when
an SM reports one (this card did not). Details in `cuda-shim/libtinynv/src/{exec.c,exec.h,gsp.c}`.

## Why the numbers do not move (checked, not assumed)

`g->dy` gets bigger (1,024 → 2,048 floats per token), which shifts the GDN backward's other work buffers down by
`1024 n` floats and nothing else. All arithmetic is untouched: the GEMMs wrote the same `[n][2048]` values before and
after, and the gated norm read the same region; the only difference is that the region is now a properly allocated buffer
instead of overlapping dead scratch (recompute) or leaving the allocation (store).

Measured, on the card, same binary, same `.jtb`, same adapter, `--batch 4 --accum 2 --max-steps 20 --trace-loss`:

so the store is byte-identical to the recompute path (20 steps, all 20 lines) **and** the fix changes no number in either

## What the guard is, and what it costs

`JT_NO_RECOMPUTE_GUARD=<KB>` (0, the default, is off): `jt_ctx_alloc` adds that many bytes above the store and fills them
with `0xA5`; `store_forward`/`store_backward` check the poison after every piece (mixer forward, MLP forward, MLP
backward, mixer backward) with one D2H copy and stop at the first byte that is not the poison, printing the layer, the
piece and the span. Off it costs one `getenv`; on it is a few MB of host copy per piece, which is how the numbers above
were read. It is left in because the store's work region is the one buffer in this system whose end is also the end of the
allocation, so a piece that writes past its own top buffer has no other way to say so.
