## What this PASS does and does not say

* **It says the trainer reproduces the arm.** Both jefftrain seeds land within the arm's own seed-to-seed variation of
  both Python seeds on all 15 `score.py` metrics, and on the two gates the design fixes numerically the margins are
  1.6x–15x. The 3,581-step trajectory is train.py's batch order (prep.py's four `.jtb` files are byte-identical across
  the three attempts), `gemm: tf32`, 12.29 GB peak, and the dev curve falls 1.1276 → 0.4582 (seed 0) / 0.4571 (seed 1),
  against the Python arm's 0.4575 / 0.4511.
* **The band now contains our own runs, so it is a weaker test than it was.** A member-vs-member difference cannot
  exceed the band that contains both, so "15/15 OK" was never going to be hard once jefftrain's seed 1 joined the pool;
  the informative parts are that our two seeds' spread is the *larger* of the two implementations on 4 of the 15 metrics
  (precision 0.056 vs 0.027, F1 0.032 vs 0.016, recall@0.9 0.035 vs 0.000, `fp`@0.5 2 vs 1) and that the residual bias
  is 2 of 15 metrics: `jev_argmax_agreement` (jefftrain 0.912/0.919 vs Python 0.931/0.925 — 1–3 of 160 lines) and
  `th0.5.maybe_cards` (15/16 vs 18/18 — 2–3 cards). Both jefftrain seeds sit on the same side of both Python seeds on
  those two.
* **Under the Python-runs-only band, the first attempt's verdict still stands**: seed 0 has 6 of 15 metrics over and
  seed 1 has 1 of 15 (`th0.5.maybe_cards`, 3 of 160 test lines). This note does not overturn that; it records the
  gate under the definition the user chose after reading it. Both numbers are in the log.
* **A known, documented difference remains:** the run starts from `make_adapter.py`'s fresh adapter (A random,
  B ~ N(0,1)·1e-2) whereas `train.py` starts with B = 0 — a ~2e-2 LoRA update at step 0, the same order as the residual
  differences above, and the likeliest cause of them. Nothing was changed to narrow it, and no kernel, gate, tolerance,
  compute mode or arm setting was touched in this card.

**Follow-up worth a small card:** `scripts/arm.sh` still takes its band from the Python runs only, so this gate is not
reproducible by the next task from the script alone. It should accept the jefftrain bands' run directories (the same
way `JT_REF_RUNS` accepts the Python ones) and print this table itself.

## The runs

Two runs, gpubox only, no card and no eGPU, each inside the approved 90-minute cap:

```
$ cd train/jeff && export JT_REMOTE=macuda-train/wt-G-m64
$ sh scripts/gpubox-build.sh                    # rebuild: the tree still held a07a7a3's main.c
$ JT_SKIP_BUILD=1 sh scripts/arm.sh soft        # seed 0  -> rc 1 (Python-only band, 6/15 over)
$ SEED=1 sh scripts/arm.sh soft                 # seed 1  -> rc 1 (Python-only band, 1/15 over)
$ ssh gpubox 'python3 - "…-080249" "…-180810" "cuda-soft-20261108-165516" "cuda-soft-20261108-173754"' < band.py
```

Wall clock 75.5 min (seed 0) and 76 min (seed 1); the J42 fix held, so prep.py's full-split `train.jtb` (28,645 rows,
3,581 batches, its one 5-row batch at index 2,845) trained all the way through in both runs. Seed 1: temperature fit
0.978229 (calibration soft CE 0.47694 → 0.47681), test T=1 soft CE 0.46691, argmax 0.9188; seed 0: T 1.019791,
test T=1 soft CE 0.48988, argmax 0.9125.

**Where the seed acts.** `jefftrain` has no `--seed` of its own: given the `.jtb` and the adapter its run is
deterministic (no dropout, no random readout init). The arm's seed enters through `prep.py`, i.e. train.py's own
`batches()` order — verified, not assumed: the seed-0 `train.jtb` puts the one 5-row batch at index 2,845, the seed-1
file at index 2,036, the two files have different md5s at the same byte count, and `dev.jtb`/`calibration.jtb`/`test.jtb`
are md5-identical (the eval splits are not shuffled). So the two jefftrain runs differ in epoch order only, which is the
same channel the Python arm's two seeds differ through (`train.py` starts from B = 0, so its init is seed-independent too).
