## 1. `scripts/ab.sh`: the interface, and why it is shaped this way

Documented in the file's header (`sh scripts/ab.sh --help` prints it). In one paragraph:

* **Side A** is `git archive HEAD train/jeff` into a fresh directory under `$TMPDIR`, synced and built by *that copy's
  own* `scripts/gpubox-sync.sh`/`gpubox-build.sh` into `~/<JT_REMOTE>-base` on gpubox — i.e. the card's start commit,
  before its edits. **Side B** is this worktree, built into `~/<JT_REMOTE>`. Both builds start from
  `ssh gpubox "rm -rf ~/<remote>/build"` first, because `rsync -a` restores the source's mtime and `make` would
  otherwise keep a stale object (design §11.3's trap).
* **Data**: `JT_AB_DATA` (default `data/ovril_detect/runs/parity-steps-latest` under `~/CLM-8B`) — the `.jtb` files
  J38-J40 timed, i.e. `py/prep.py`'s 256 train rows / 64 dev rows at `--batch 8 --accum 1 --seed 0` and
  `py/make_adapter.py`'s adapter. Defaults `--batch 8 --accum 1 --max-steps 20`, TF32; `--exact` switches to
  `JT_EXACT=1 TINYCUBLAS_TC=0`.
* **Measurement**: `P` pairs (default 3), interleaved A B A B …, each run's median s/step over steps 3..N (plan M6.3's
  warm-up rule) and its peak memory, then each side's median (median of its P run medians) and spread (max−min), the
  relative difference, and `WORTH: yes|no`.
* **`--same`**: one run per side in exact mode, with `--trace-loss` and `--eval dev=<dev.jtb> --eval test=<test.jtb>`,
  then `cmp` of `steps.jsonl`, `pred-dev.jsonl` and `pred-test.jsonl`; prints `BITEXACT: yes` only if all three match.
  "The same seed" is the same prepared data and adapter — jefftrain has no RNG at all (`grep -rn srand src/` is empty),
  so the seeds that exist are `py/prep.py`'s and `py/make_adapter.py`'s.
* **Per-side env and log check**: `--env-a`/`--env-b 'JT_A=1 JT_B=2'` add settings to that side's jefftrain
  environment, and `--expect-a`/`--expect-b '<ERE>'` fail a run whose log has no matching line.
* **Lock**: the whole remote part is one `ssh gpubox "… exec flock ~/macuda-train/.gpu.lock env … sh -s"`, and `flock`
  is checked first (`/usr/bin/flock` exists there), so a missing `flock` fails with a message instead of running
  unlocked.
* Logs, traces and the run directory stay in `~/CLM-8B/data/ovril_detect/runs/ab-<UTC stamp>/` on gpubox.

One shape fact worth writing down, because it cost a run: `prep.py` writes **eval/dev splits at 2× `--batch`** and
jefftrain opens them at `ev_batch = a.batch * 2 > 2 ? a.batch * 2 : 2` (`src/main.c:1633`), so `--same`'s `test.jtb` must
be prepped with the same `--batch` as the run, not with parity-eval's `--batch 4`. The first `--same` attempt was
rejected with `160 row(s) in 20 batch(es) is not what --batch 16 --epochs 1 implies (10 batches)`; after the fix
`prep.py --eval test=… --batch 8 --accum 1 --epochs 1` writes 10 batches and both sides run.

## 2. The four gpubox scripts: `JT_ENV`, `JT_EXPECT`, and the lock

Added to `arm.sh`, `parity-eval.sh`, `parity-steps.sh`, `timing.sh`, in the same form in each:

* `JT_ENV="JT_A=1 JT_B=2"` → appended to the jefftrain command as `env $EXACT_ENV $JT_ENV "$BIN" …`, so it lands in
  the remote jefftrain's environment and nowhere else.
  **Checked on the Mac before it reaches ssh**: every whitespace-separated word must match
  `^JT_[A-Z0-9_]+=[A-Za-z0-9._-]*$`, else the script prints which word was refused and exits 2. The four scripts check
  in the same place they take `JT_REMOTE` (before `gpubox-build.sh`), and `parity-steps.sh` checks *before* its
  `exec ssh` hop as well as forwarding the two variables through it, so a run started from the Mac is validated on the
  Mac.
* `JT_EXPECT='<regex>'` → `grep -Eq -- "$JT_EXPECT" <jefftrain log>` after the run, and the script fails if it does not
  match. `arm.sh`/`timing.sh`/`parity-eval.sh` already keep their run's log (`$RUN/jefftrain.log`, `$d/jefftrain.log`,
  a `mktemp`); `parity-steps.sh`'s C step printed straight to the terminal, so it now also keeps `$RUN/c.log` and
  `cat`s it, i.e. the same lines as before plus the checkable file.
* **The lock**: `arm.sh`, `parity-eval.sh` and `timing.sh` wrap their single ssh in
  `flock ~/macuda-train/.gpu.lock env …`; `parity-steps.sh` runs on the box itself, so it re-execs itself once under
  `exec flock ~/macuda-train/.gpu.lock sh "$0" "$@"` (guarded by `JT_LOCKED=1`) after the hop decision — its Python
  trace and its C step both use the card, so the lock covers the whole run. Each checks for `flock` first and fails with
  "flock is missing on gpubox" rather than running unlocked.
* With both variables unset, nothing else moved: same arguments, same output, same verdicts, still exit 0/1 on the same
  lines. The only visible additions are the retained logs named above (plus `c.log` for parity-steps).
* A vocabulary limit worth knowing: `JT_ENV` words must start with `JT_`, so `TINYCUBLAS_TC=0` cannot be smuggled in
  through it. Exact mode is `ab.sh --exact` (both sides) or `EXACT=1` on the M6 scripts, exactly as before.

Verified without running the four long scripts, by putting a fake `ssh` first on `PATH` and reading its argv
(`JT_SKIP_BUILD=1`, `JT_REMOTE=macuda-train/wt-J43-test`):

```
FAKE-SSH-ARGV: … exec flock ~/macuda-train/.gpu.lock env JT_REMOTE='macuda-train/wt-J43-test' ARM='soft' … \
  JT_ENV='JT_A=1 JT_B=2.5' JT_EXPECT='^ctx: no-recompute \(JT_NO_RECOMPUTE\)' sh -s
FAKE-SSH-ARGV: … exec flock ~/macuda-train/.gpu.lock env JT_REMOTE='…' BATCHES='8' … JT_ENV='JT_GDN_CHUNKED=0' \
  JT_EXPECT='^ctx:' sh -s
FAKE-SSH-ARGV: … exec flock ~/macuda-train/.gpu.lock env JT_REMOTE='…' MAXDP='0.05' … JT_ENV='JT_X=1' \
  JT_EXPECT='ctx' bash -s
FAKE-SSH-ARGV: cd ~/macuda-train/wt-J43-test && JT_REMOTE='…' JT_ENV='JT_X=1 JT_Y=' JT_EXPECT='gemm: exact' \
  sh scripts/parity-steps.sh
```

i.e. both variables survive quoting (including a regex with parens and an empty value), and each script's GPU work is
inside the lock.

```
$ export JT_REMOTE=macuda-train/wt-J43
$ sh scripts/ab.sh --steps 6 --pairs 1                     # 56 s, both builds + two runs
=== A run 1: ~/macuda-train/wt-J43-base/build/nv/jefftrain -> …/ab-20261110-221036/A-1
ab: A run 1: median 0.8950 s/step over steps 3..6, peak 11.24 GB, 13s wall

ab: B run 1: median 0.9050 s/step over steps 3..6, peak 11.24 GB, 15s wall
ab: side A median 0.8950 s/step, spread 0.0000 (1 run(s))
ab: side B median 0.9050 s/step, spread 0.0000 (1 run(s))

ab: worth needs B >= 1.5% faster and gap > 3x the larger spread

```

With one pair each side has no spread by construction, so the stronger demonstration is the same 6-step shape at three
pairs (`JT_SKIP_BUILD=1`, i.e. the binaries the 1-pair smoke had just built, 84 s):

```
$ sh scripts/ab.sh --steps 6 --pairs 3
ab: A run 1: median 0.9050 s/step … peak 11.24 GB, 14s wall      (runs 2 and 3 identical)
ab: B run 1: median 0.9050 s/step … peak 11.24 GB, 14s wall      (runs 2 and 3 identical)
ab: side A median 0.9050 s/step, spread 0.0000 (3 run(s))
ab: side B median 0.9050 s/step, spread 0.0000 (3 run(s))
ab: B is 0.00% faster than A; the larger spread is 0.0000 over 3 and 3 run(s), gap +0.0000
WORTH: no
```

Six runs of the same code, one number to four decimals: the tool reports no difference, which is what "you changed only
scripts" has to look like.

**The noise floor, measured, because later cards need it.** Across the smoke invocations of this card the *same* binary's
6-step median moved between **0.890 and 0.915 s/step** (±1.4%), so a naive single run can show a 1.5% "win" from nothing.
The clearest example (a 2-pair run, `ab-20261110-221108`):

```
ab: side A median 0.8900 s/step, spread 0.0000 (2 run(s))
ab: side B median 0.9100 s/step, spread 0.0100 (2 run(s))
ab: B is 2.25% slower than A; the gap -0.0200 is below the larger spread 0.0100
WORTH: no
```

— 2.25% between two sides that are the same code, refused by the 3× spread rule. That is the rule doing its job, and it
is the number to keep in mind when a later card reads `WORTH: yes`: at 20 steps the medians are steadier (1.100 vs
1.105 in §3.3) but the between-invocation drift is the same order. Two side notes on why the two sides' binaries are
not byte-identical even though their code is: A vs B differ in 18–27 bytes, **all inside `.strtab`** (generated symbol
names — hex digits); `.text` and `.nv_fatbin` are byte-identical, and so are all their outputs (§3.3). Two builds of the
*same* tree at two paths differ in exactly the same 27 bytes (`wt-J43` vs a scratch `wt-J43-c`), so it is a
build-path artefact, not a source difference.


And the positive control, on the same shape: `--expect-b '^gemm: tf32'` → `ab: B run 1: log matches /^gemm: tf32/` and
the run proceeds to the WORTH line.

`--env-b` reaching jefftrain's environment was checked end to end rather than assumed: `--env-b 'JT_EXACT=1'` (no
`--exact`) changed the trainer's own mode line, and the run was then rejected by the same compute-mode check `arm.sh`
uses:

```
ab: side B env: JT_EXACT=1
ab: model /home/user/models/jeff-base  compute 'gemm: tf32'
ab: B run 1: expected 'gemm: tf32' on stdout, got:
  | gemm: exact fp32
exit 1
```

The four edited scripts' own `JT_EXPECT` check is the identical two lines (`[ -n "$JT_EXPECT" ] && ! grep -Eq -- …` →
message + non-zero exit); I did not run them for real — they are the 20-step/100-step/arm-length runs the task said not
to run — so the evidence for that path is this one, on `ab.sh`, plus the argv check in §2.
