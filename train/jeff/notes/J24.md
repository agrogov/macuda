## The change (one new file, `src/main.c`; `src/model.c` needed nothing)

`src/model.c` already had everything this step needs — J18 (M4.2) wrote `model_load`, `jt_batch_set`, `jt_ctx_alloc`,
`layer_fwd` and `model_forward`, and the four M4.3 pieces landed under it in J19–J23. **This task is `model_forward`'s
first whole-model exercise**: the embedding gather, 24 layers in sequence (18 GDN, 6 attention, 6 of them the MLP-only
boundary), then `head_fwd`, in one sweep on a packed batch. It passes with no change to `model.c`, so `model.c` is
untouched here (the whole-model driver it owns is what the numbers below prove).

The new file is the driver:

| flag | what it does |
|---|---|
| `--model DIR` | `model_load` (the st_get shape checks) + `lora_alloc`; the checkpoint directory or its `model.safetensors` |
| `--init-adapter DIR` | `lora_load_adapter` over the checkpoint's readout — train.py's flag, and the parity runs' entry point |
| `--train FILE.jtb` | train.py's flag for the split a run consumes (plan M5.2); `--dump-forward` reads its **batch 0** |
| `--dump-forward OUT` | the whole forward on that batch, written in `py/dump_ref.py`'s format |
| (no arguments) | usage, exit 0 (a binary that runs under `make test-null`-style automation must not fail for nothing) |
| `--train` without an action | loads everything, then says the training step is plan M5.2 and exits **2** — a run that did no work must not look like a run |

`--dump-forward`'s keys are exactly dump_ref.py's **forward** keys (`in.ids`, `in.off`, `layer.{i}.in`,
`layer.{i}.post_mixer`, `layer.{i}.out` for i = 0..23, `final`, `logits`, `loss` — 77 keys), written with `st_write`
(design §9.2). Three decisions worth recording:

* **The batch is the fixture's batch 0**, packed back to back (design §7) and built from the .jtb itself: the rows' ids
  concatenated, the per-row live option count and weight, the targets zero-padded to the widest row's live count — the
  same arrays `train.py`'s `collate` and `dump_ref.py` feed their own copy of the loss. `gw` is the batch's summed row
  weight, i.e. `train.py`'s `(per * wt).sum() / gw`.
* **`in.ids` / `in.off` are F32, not I32.** `src/st.h`'s writer is F32-only (design §9.2) and it is not this task's file.
  Every id is below `MT_VOCAB` = 248320 and every offset below the token count, all exact in fp32, and
  `compare_layers.py` compares an integer key against a float one by value (`to(int64)` on both) — so the check is still
  exact, and it prints `exact  ok` (see the runs below).
* **The arena is sized for the batch the dump runs** (`cap_tokens = N`, `cap_rows = B`, `lmax` = the longest row), not
  for a training .jtb's worst case: the dump runs one batch, and a trainer that sized it from `max_tokens_per_batch` would
  pay 1.65 GB of arena for a 107-token probe. Everything else — the 25 activation slabs `model_forward` fills, the 24
  `post_mixer` slabs the dump wants, the gathered logits — is device memory the dump copies back once and writes.

### One thing to know before M4.4 / M5.1: the key sets differ, and `compare_layers.py` counts that as a failure

`ref.safetensors` has **403** keys (77 forward + 326 `grad.*`). `--dump-forward` writes the 77 forward keys; a forward
cannot produce gradients (plan M5.1's `--dump-backward` is where those appear). `compare_layers.py` treats a reference key
missing from the other file as `FAIL (not in …)`, so run against the **full** ref it prints `77 ok, 326 failed` and exits
**1** even though every forward key passes. Both files are other tasks' (`py/compare_layers.py` is J14's,
`scripts/card-check.sh` is M0.4's), so they are untouched here; the numbers below are given both ways:

1. against `~/macuda-train/ref/ref.safetensors` itself — **every `layer.{i}.out`, `final`, `logits` and `loss` `ok`**,
   326 keys of the file fail only for being `grad.*` and not written;
2. against the **forward subset of that same file** (`/tmp/j24/ref-fwd.safetensors`, made on gpubox with a throwaway
   `safetensors` one-liner: `{k: v for k, v in load_file(ref).items() if not k.startswith("grad.")}`, 77 keys, 7,998,585
   values, every tensor byte-for-byte the ref's) — `77 ok, 0 failed`, **exit 0**.

Consequence for **M4.4** (the card checkpoint): `scripts/card-check.sh <A|B> m4` ends with
`compare_layers.py "$JT_REF" "$out"` against the full ref, so it will count 326 failures and `checkpoint m4: 1 steps,
1 failed` **until** the forward-only key set is accounted for — either `JT_REF` points at a forward-only extract (as in 2),
or the m4 step waits for `--dump-backward` (which M5.1 writes, and which should then write all 403). That is a decision
the next task's owner (or the user) has to take; it is not a defect in the dump.

## Numbers worth recording for the later tasks

* **The whole forward is 2.1e-06 relative** (`final`, N = 107, exact build) against the fp32/eager/literal-GDN CPU
  oracle, worst of all 77 keys; per-layer 6.1e-08…1.3e-06; `loss` 3.4e-07; live logits 2.6e-07. M4.4's card run compares
  the same file, so a card failure is the shim, not the arithmetic, unless it is the GDN/attention kernels' summation order.
* **TF32 is 8.9e-04 on `final`** (0.9x of the gate!) — M6/M4.4 runs that are not `JT_EXACT=1` have almost no margin on
  this metric; the exact build is the one to trust.
* Dump cost at the fixture: **0.45–0.49 s wall with the checkpoint in page cache** (1.3 s on the first, cold read of
  the 2.5 GB checkpoint; the load alone is 0.31–0.35 s), so the sweep + head + 21 MB readback + 21.5 MB write is about
  0.12–0.15 s for 107 tokens. 21.5 MiB of data, 77 keys. At the plan's
  batch (B = 8, N = 4200) the same code holds 49 slabs of `N x 1024` = **824 MB** of device memory plus a 1.65 GB arena —
  fine for the dump on a 5090 but 3x the training step's activation budget, which is why `model_forward` itself keeps only
  the 25 layer-input slabs (design §6.2) and the `post_mixer` slabs are this flag's cost.
* `--dump-forward` sizes the arena from the batch it runs (`cap_tokens = N`), the trainer (M5.2) must size it from the
  .jtb's `max_tokens_per_batch`/`max_len` and scan every batch, not just batch 0.
* For **M5.1** (`--dump-backward`): the ref has 403 keys; adding `grad.layer.{i}.out` (24), `grad.final`, `grad.readout`
  and 300 LoRA factors to the same file makes `compare_layers.py` self-consistent against the full ref again (the
  `--grad-rel 5e-3` branch), and that is what makes `card-check.sh m4|m5` work with `JT_REF=ref.safetensors` unchanged.
  The forward half of that file is already exactly this dump's.
* Layering for the trainer: `model_forward(ctx, ids, n, b, saved_in, post_mixer)` runs `JT_FWD_ONLY` for all 24 layers
  and needs 25 × `n` × 1024 floats of `saved_in` (2.7 MB at the fixture, 430 MB at N = 4200); the head reads
  `saved_in + 24*stride`. `layer_fwd` copies the post-mixer residual when `post_mixer != NULL` (one extra D2D pass per
  layer) — pass NULL in a training step and the copy disappears.
