## The format, as implemented (design §9.1 — M5's prep.py must match this)

```
"JTB1" | u32 version=1 | u32 n_rows | u32 n_batches | u32 max_tokens_per_batch | u32 max_len | u32 max_opts   (28 B)
u64 offset[5]                                                                                                 (40 B)
rows     n_rows x { u32 len, u32 n_opts, f32 weight, u32 teacher_top, u64 id_offset_in_strings }              (24 B each)
ids      sum(len) x u32, row by row
targets  sum(n_opts) x f32, row by row
batches  n_batches x { u32 n, u32 row_index[n] }
strings  per row: id NUL, then each criteria key NUL-terminated, then an empty string (a final NUL)   -> "fx-0000\0A\0B\0\0"
```

Little-endian, no padding. The section table starts at offset 28 (not 8-byte aligned), so the row records are read
with `memcpy`, never a cast; the ids/targets sections are checked to be 4-byte aligned because they are handed out as
`const uint32_t *` / `const float *` into the map.

Two things the design leaves open, decided here and written down in `src/jtb.h` and `py/make_fixture.py` so prep.py
cannot guess differently:

* `id_offset_in_strings` is **relative to the start of the strings section**, not to the file.
* the header's maxima are the file's **actual** maxima: `max_len` = longest row, `max_opts` = widest row,
  `max_tokens_per_batch` = the largest batch's sum of `len` (what the arena is sized from, design §6.2).

`jtb_open()` validates more than §9.1's list, all with a message and `exit(1)` (the `st_get()` convention):
magic, version, every offset ascending/inside the file/4-aligned, a section's length being exactly the next offset
minus its own, `len`/`n_opts` sums equal to the ids/targets section sizes (the plan's check), `max_len`/`max_opts`
bounding every row, `teacher_top < n_opts`, weight ≥ 0, every token id < 248320, targets in [0, 1] summing to 1
(±1e-3, the same bound `encode()` in train.py uses at 1e-4), every id NUL-terminated and non-empty, the key list
NUL-terminated and its length equal to the row's `n_opts`, and every batch non-empty, in range, without a repeated
row, within `max_tokens_per_batch`, the batches section consumed exactly and covering at least `n_rows` rows. None of
these are tolerances a test could be made to pass by loosening — they are format invariants.

API (`src/jtb.h`): `jtb_open`/`jtb_close`, header getters (`jtb_n_rows`, `jtb_n_batches`, `jtb_max_tokens_per_batch`,
`jtb_max_len`, `jtb_max_opts`, `jtb_version`, `jtb_file_size`), `jtb_section_offset/_size` (so a test can compare the
sums with the section sizes), and the plan's accessors `jtb_row`, `jtb_ids`, `jtb_targets`, `jtb_batch(j,k,&n)`,
`jtb_id`, `jtb_keys(j,i,out[],max)` (returns the count, `-1` if it does not fit). `JtbRow` carries two derived members,
`ids_off`/`tgt_off`, so the accessors are O(1).

## `py/make_fixture.py`

```
--seed 1 --rows 8 --out f.jtb [--min-len 8] [--max-len 120] [--batch 4] [--min-opts 2] [--max-opts 6]
[--lengths L1,L2,...] [--opts N1,N2,...]
```

Random ids < 248320, lengths in [8, 120], n_opts in [2, 6], targets = softmax of `random()` scores (so
`teacher_top` is the clear argmax), weights 1.0, ids `fx-0000`…, criteria keys `A`, `B`, … `Z`, `AA`… (Excel-style,
so n_opts may exceed 26 up to 255), batches = consecutive chunks of `--batch` rows in row order (the real order comes
from prep.py in M5).

`--lengths` / `--opts` were in from the start, for design §10.2's two rows (M4.1/M4.4):

```
python3 py/make_fixture.py --seed 1 --rows 2 --lengths 37,70 --opts 5,12 --batch 2 --out /tmp/fx2.jtb
```

`--rows` may be omitted when `--lengths`/`--opts` are given; a mismatch, `--rows 0`, `--batch 0`,
`min-len > max-len` or `--opts`/`--max-opts` outside 1..255 is a usage error (exit 2). The same seed gives
byte-identical files.

## `test/test_jtb.c`

Takes the fixture as `argv[1]`; **with no argument it prints that it skipped and exits 0** (the README's convention, so
`make test-null` and a card checkpoint's `DRY=1` stay green). It checks the plan's sums (Σlen·4 = ids section,
Σn_opts·4 = targets section, n_rows·24 = rows section), that `max_len`/`max_opts` are the rows' maxima, that every id
is < 248320 and every target set sums to 1 with an argmax at `teacher_top`, the ids (`fx-%04d`) and key lists, the
batches (in range, no repeat, token sum, coverage, and `jtb_batch`/`jtb_row` returning NULL past the end). Then it
copies the fixture, flips one byte and re-runs itself as `--expect-error <file>` (fork + pipe, stderr captured): the
reader must exit 1 with a message mentioning the thing that was corrupted. Three cases: byte 0 of the magic, byte 3 of
the first token id (id ≥ 2^24), and byte 4 (version). Exit codes: `--expect-error` returns 2 if the corrupt file
opens, so a reader that loses a check cannot pass by luck.

## Notes for the tasks that build on this

* M4.1/M4.4: `make_fixture.py --rows 2 --lengths 37,70 --opts 5,12 --batch 2` is design §10.2's batch (lengths 37/70,
  n_opts 5/12). `--opts` is the flag the plan did not spell out; `--lengths` was required and is there.
* M5 (prep.py) must write exactly the layout above; `src/jtb.h`'s comment block and this note are the contract. In
  particular: strings offsets are section-relative, the maxima are the actual maxima, and a row's criteria-key count
  must equal its `n_opts` (the reader rejects the file otherwise, and `jtb_keys` then feeds `pred-<name>.jsonl`).
  `prep.py` should write one batch per `batches(...)` call, epoch by epoch, as the design says; the reader only
  requires every batch non-empty, in range, duplicate-free and the whole file covering at least `n_rows`.
* The reader is `mmap`-based and immutable; it allocates only the parsed row table (24 B/row). `jtb_open` is fatal on a
  bad file, so `main.c` can just call it.
* `test_jtb` becomes a `build/shim/test_*`/`build/nv/test_*` binary automatically (wildcard Makefile) and is linked
  against `src/jtb.c` only in `make test-cpu`; every other test binary on the GPU builds also links `host_jtb.o`
  because it is a `src/*.c`. That is intended (no CUDA calls in it).
