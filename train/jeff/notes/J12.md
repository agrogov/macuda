## Decisions worth reading before the next task

* **The model table lives in `src/model_table.c/.h`, not in `model.c`** (design §13 names `model.c`). `src/lora.c`
  needs the table before `model.c` exists (J18), so it is its own file and J18's `model.c` includes it from there
  rather than growing a second list of names. **Note for J41 (docs):** design §13's file list should say
  `src/model_table.c/.h` and `model.c` should be described as the loader that consumes it.
* **The table is verified against the real checkpoint**, read-only, nothing copied into macuda:
  * all 320 tensor names it holds exist in the real `model.safetensors` header with exactly the shapes it claims
    (the 1-D norms, `A_log`/`dt_bias` `[16]`, `conv1d` `[6144,1,4]`, `in_proj_a/b` `[16,1024]`, the 150 adapted
    `[out,in]`), and no `language_model.layers.*` tensor of the checkpoint is missing from it (473 tensors total in
    the file; the visual/mtp ones are skipped as design §3.2 says);
  * the 300 adapter keys that `lora_save_adapter` writes are **exactly** the set
    `tools.jeff_lora.lora.attach_lora(AutoModel.from_config(real config), 16, 32)` produces
    (`{stem}.lora_A` / `{stem}.lora_B`, 150 layers, stems `language_model.layers.{i}.…`) — checked with CLM-8B's
    venv against the file this test wrote, both files (the fixture and the saved copy), set equality 300/300. That is
    design §9.2's "the key set must match exactly".
* `adamw_step` takes `bias1`/`bias2` (pre-computed on the host in double, passed as floats) instead of the step
  count `step_t` of the plan's shorthand, as the same plan sentence asks; `kernels/adam.h` says so.
* `sumsq_partial`/`sumsq_final` take the block count as a parameter (`K_ADAM_BLOCKS` = 1024, the `k` side's fixed
  launch) so the reference and the test can also check a small ragged one. `ref/adam.h`'s `REF_ADAM_BLOCKS` is the
  same 1024. Block b owns the arithmetic progression `i = b, b+nblocks, …` and 256 threads share that slice, so the
  partials are comparable one by one, not only their sum — that is what pins the slicing (a wrong slice map still
  sums to the same total).
* `ref_linear_bwd` takes `W` as well as `A`/`B` (design §4.2's `dx = dy W + e A`); design §13's `Linear` keeps `W`
  in the struct, a CPU reference needs it as an argument. dA/dB accumulate (`+=`), dx is written, `W`-only and
  A/B-NULL paths both work.
* `lora_save_adapter` has a fifth, nullable argument (`const LoraMeta *`: base path, targets, weights) beyond the
  plan's `(dir, step, dev_ce)`, because train.py's `save_lora` writes those into `adapter_config.json`; M5's `main.c`
  already knows them. `adapter_config.json` is written with a few lines of `fprintf` inside `lora.c` for now — when
  `src/json.c` exists (design §13, another task) that belongs there; noted for J41 too.
* `lora_load_adapter` reads design §9.2's own keys first, and also accepts PEFT's spellings
  (`{stem}.lora_A.weight`, `base_model.model.…`) so an adapter produced by a different pipeline loads too; the
  shape/dtype check is the same either way. The readout is accepted as F32 or BF16 (a checkpoint's
  `readout.safetensors` is bf16, ours is fp32) and both are tested.
* `lora_alloc` zeroes all four buffers and does not invent an init: design §2.1 says jefftrain never reproduces
  torch's RNG, and a parity run starts from `--init-adapter`. Whatever a non-parity run starts from is M5's
  `main.c`'s call.
* `lora_zero_grad` (one `cudaMemsetAsync`) is the only extra function beyond the plan's list; it is what the flat
  buffer's "one launch" argument (design §8.1) needs at the start of every accumulation group.
