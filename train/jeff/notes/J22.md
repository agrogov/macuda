| `out = o_proj(o)` | `linear_fwd` (u saved) |
| `x_out = x_in + out` | `cudaMemcpyAsync` (skipped when `x_out == x_in`) + `jt_add_inplace` |

Decisions worth recording, each written down in the file's header comment where it matters:

* **The save layout is one function.** `attn_saves(c, n, mode, &s)` takes the 15 buffers in a fixed order from the
  arena's *save* half in `JT_FWD_SAVE` and from its *work* half in `JT_FWD_ONLY` (same arithmetic, different half, and
  a `JT_FWD_ONLY` call gives every word back before it returns). The bwd takes no activation pointers, so it will call
  the same function to land on the same pointers; there is no second table to get out of step. The 15 buffers are
  `r_in, a, qg, q_pre, r_q, q, k_raw, r_k, k, v, o_pre, u_qg, u_k, u_v, u_o` = **12,875 floats per token** (measured
  below, not estimated), which leaves the MLP's ~11.8 K/token saves room inside `JT_ARENA_FLOATS_PER_TOKEN` (98,304).
  `gate` is not saved: the bwd re-splits it out of `qg`. `P` is not saved either — the bwd recomputes it row by row,
  which is what the arena's `2 x 8 x lmax^2` term is for.
* **One row at a time, sized by `c->lmax`.** The head-major q/k/v/o (`[8][lmax][256]` each), `kv_expand`'s token-major
  `[lmax][2048]` scratch and the `[8][lmax][lmax]` scores and probabilities are allocated once per call and reused by
  every row, so a batch costs its longest row and not the sum (design §6.2, §8.2). At the plan's worst case
  (`lmax = 1026`) that is 10,240 x 1026 + 2 x 8 x 1026^2 = 27.3 M floats = 109 MB, over and above the per-token arena.
* **The GQA group is `h/4`, not `h%2`.** `group = MT_FULL_HEADS / MT_KV_HEADS` is passed to `jt_kv_expand`, which lays
  head `h = g*group + r` where the batched GEMM then reads it — so query head 5 reads KV head 1, as design §3.5 says.
* **Row-local RoPE for free.** `rope_fwd` takes the batch's own `off_dev`/`row_of`, so row 1's first token is position 0
  and not the packed index 37 (design §7); the reference's second row is 70 tokens long, so a packed-position bug
  cannot pass this test (see the negatives below).
* **Argument checks return `JT_LAYER_FAIL`, never `exit()`**: null context/weights/x_in/x_out/batch, `n != b->n`, an
  invalid mode, negative `n`, an `off` table that is not a prefix sum up to `n`, and a row longer than `c->lmax` (which
  would read past `rope_cos`/`rope_sin` and past the row buffers). `n == 0` is `JT_LAYER_OK` with no work. A failed
  `linear_fwd` is passed through after `jt_work_restore`, so a partial call never leaks arena words.

### The gate is not vacuous — the plan's suspects

The plan says that if layer 3 fails, suspect "the q/gate interleave, the RoPE positions (local vs packed), the
head-to-group mapping (h/4, not h%2), and the q_norm offset (1+w)". Two of those are one-token changes, so I ran them
in the gpubox copy (patched with `sed`, run, then re-synced away; the worktree never saw them):

| variant | layer 3 result |
|---|---|
| `q_norm` as `w` instead of `1 + w` (`zero_centred 1 -> 0` in the q_norm call) | **rel 8.870e-02 FAIL** |
| the two qgate_split outputs swapped ("q = the last 2048", the interleave bug) | **rel 2.264e+00 FAIL** |

The other two are caught by construction rather than by a patch: a packed-position bug would apply positions 37…106 to
row 1 and read `rope_cos` out of bounds (the table has 70 rows), and an `h%2` group mapping permutes which KV head each
query head reads — both change `post_mixer` far more than 1e-3, and the numbers above show they are not happening.

## Numbers worth recording for the later tasks

* Per-token arena for the attention mixer's forward: **12,875 saved floats + 5,120 work floats** (`gate`, `o_gated`,
  `out`) = 17,995 of the 98,304 budget; with the MLP's ~11,825/token saves a layer's `JT_FWD_SAVE` pass uses about
  24,700/token, a 4x margin at N = 4200. Per-row, above and beyond that: 10,240 x lmax + 16 x lmax^2 floats (109 MB at
  lmax = 1026, 0.5 MB at the fixture's lmax = 70).
* Per-row work at the fixture's geometry: 8 batched GEMM-dispatch pairs (one `[L,L,256]` and one `[L,256,L]` per row for
  all 8 heads at once) + 6 elementwise/transpose kernels per row. At L = 1024 a row's scores GEMM is 8 x 1024 x 1024 x
  256 x 2 = 4.3 GFLOP and PV the same, i.e. about 8.6 GFLOP per row for the whole mixer — the reason design §8.2 is
  happy with the simple route and no flash attention.
* The forward's error against the fp32 CPU reference is 1.5e-07 … 5.6e-07 over the six attention layers, so the
  gain from here to the plan's 1e-3 gate is about 3,200x; whatever the MLP and the head add, the mixer is not what
  will use it up.
* `attn_softmax_fwd` applies the 1/16 inside, so the caller passes the raw GEMM scores (design §8.2). The backward must
  pass the same `scale` to `attn_softmax_bwd`; `ATTN_SCALE` is the one definition.
