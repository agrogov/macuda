## What the two files do

`py/prep.py` imports CLM-8B's `tools.jeff_lora.train` (`read_jsonl`, `encode`, `balance`, `batches`,
`default_model`) and `prompt.load_decision_config` by path from `--clm`; it never copies their code (design §9.1).
It reproduces `main()`'s RNG sequence call for call:

1. `random.Random(seed).sample(train_rows, --train-rows)`;
2. `random.Random(seed + 1).sample(dev_rows, --dev-rows)`;
3. `encode(train, decision, tok, hard = --targets hard)`, `encode(dev, …, False)`, then `balance(train,
   --weight-cap)` with `--weights balanced`;
4. one `rng = random.Random(seed)`, consumed **only** by `batches(train, --batch, rng, shuffle=True)`, called once per
   epoch in epoch order; all epochs' batch lists go into `train.jtb`, one batch record per `batches()` result;
5. `batches(rows, --batch*2, random.Random(0), shuffle=False)` for dev and `max(2, --batch*2)` for each `--eval`
   `NAME=PATH`.

It writes the JTB1 layout exactly as `src/jtb.h` reads it (magic/version/6 u32 header, `u64[5]` section table, rows,
ids, targets, batches, strings with the id then the criteria keys then an empty string; `id_offset_in_strings`
section-relative; the header's three maxima are the file's actual maxima). Next to `<name>.jtb` it writes
`<name>.prep.json` with the arguments that shaped it (see the deviation below).

`py/trace_train_order.py` is the evidence: it wraps `T.batches`, runs `T.main([...])` with the plan's run
(`--train-rows 64 --dev-rows 16 --epochs 2 --batch 8 --max-steps 16`), records every call's rows (id, len, weight,
teacher_top) to `--trace-out`, runs `py/prep.py` with the same arguments, reads `train.jtb`/`dev.jtb` back with its
**own** JTB1 parser (not prep's writer, and it re-checks the invariants `src/jtb.c` enforces), and compares:

* train: the traced calls flattened, batch by batch, row by row, against `train.jtb`'s batches, plus the per-call
  grouping (each `main()` call must be a contiguous run of prep's batches);
* dev: **every** `evaluate()` call (there are three: start, end of epoch 1, end of epoch 2) must equal prep's single
  dev batch list, since `shuffle=False`;
* weights: every traced row's weight against the f32 prep wrote for the same id, `1e-6`;
* determinism: prep is run a second time and both `.jtb` files must be byte-identical.

`--replay TRACE.json` re-runs only the comparison against a saved trace (a few seconds, no train.py), which is how the
throwaway mutations below were checked; `--prep PATH` points the comparison at another copy of prep.py.

|---|---|---|---|

31,749 tokens in seed 0's 64 train rows (34,296 in seed 1's); the 64-row subset is identical for `--weights none` and `balanced`
(balance only rewrites the weight field), while seeds 0 and 1 pick different subsets — checked explicitly:
`seed0 none == seed0 balanced (order): True`, `seed0 == seed1: False`.

Order (independent of the device):
`epoch1 batch1 = ovril-s00154-31, ovril-s00229-65, ovril-s00058-41, ovril-s00350-30, …`;

and shuffles the batch order again, so only the Python call reproduces it — which is exactly design §2.3's point.

Determinism: prep was run twice per test and the two `.jtb` files were byte-identical every time, e.g.
seed0-none `train.jtb` sha256 `62867746841e1ac4…`, `dev.jtb` `8ee4eebff513c180…`; seed1-balanced `8a30af073ea28a22…`
and `7703e9c546eba89c…`. `dev.jtb` is the same file for `--weights none` and `balanced` at one seed, as it must be.
The traces themselves are `/tmp/j15-trace/<seed>-<weights>/trace.json` (e.g. seed0-balanced `11da0f7ad23cf5ef…`).

Cost: ~4 min per run on the Mac's internal MPS GPU (11–19 s per step, three dev checks at ~11 s), plus 3 s per prep
run. No gpubox, no card.

## Two deviations later tasks must know about

1. **The JTB1 header cannot carry `--batch/--accum/--epochs`.** Design §9.1 says `--accum` is "written into the header
   so jefftrain can check its own flags match", but the format M1.4 implemented and `src/jtb.h`/`src/jtb.c` read has
   six u32 header words (`version, n_rows, n_batches, max_tokens_per_batch, max_len, max_opts`) and a five-entry
   offsets table at byte 28 — there is no room, and `src/jtb.*` is not this task's file to change. So prep.py writes
   those arguments, plus `source`, `row_weights`, `eval_batch`, `tokens` and the header echo, to
   `<name>.prep.json` next to each `.jtb`. **M5.2** should read that sidecar for its "reject a flag combination that
   disagrees with the .jtb" check instead of looking for header fields that do not exist. (What the header *does*
   give is `n_rows`, `n_batches`, `max_len`, `max_opts`, `max_tokens_per_batch` — enough for arena sizing and for
   `n_batches == epochs * ceil(...)` if a task prefers to check it that way.)
2. **`--eval` order is covered by rule, not by a separate trace.** `evaluate()` walks exactly the
   `batches(rows, size, Random(0), shuffle=False)` path for every split, dev included, with
   `size = max(2, batch*2)`; the green dev comparison therefore covers the eval rule, but no trace.json in this task
   contains an `--eval` split. M6.1 re-runs prep.py on gpubox for `test.jtb` anyway.

## Notes for the tasks that build on this

* **M5.2 / jefftrain**: `--train/--dev/--eval NAME=PATH` take the `.jtb` files; step through `jtb_batch(0..n_batches-1)`
  in file order and start a new accumulation group every `accum` batches, restarting the grouping at each epoch
  boundary — prep wrote epoch 1's batches first, then epoch 2's. `n_batches` is the step count only after dividing by
  `accum`.
* **M6.1** (eval parity): `$VENV/bin/python ~/macuda-train/jeff/py/prep.py --clm $HOME/CLM-8B
  --eval test=$DATA/test.jsonl --batch 4 --out-dir <data/ or /tmp>` → `test.jtb`, then `jefftrain --eval-only
  --eval test=test.jtb --eval-temperature <T>`. Outputs stay under CLM-8B's `data/` or /tmp (plan rule 5).
* **M6.2** (step parity): the same command with `--train … --dev … --train-rows 256 --dev-rows 64 --batch 8
  --epochs 1 --seed <seed>` gives the rows *and* the order the Python arm used with the same arguments; the Python
  side's step list comes from `py/trace_train_loss.py` on the same `random.Random(seed)` sequence.
* `py/prep.py` needs no GPU and no weights — only the tokenizer and `decision_config.json` from the checkpoint.
* `py/trace_train_order.py` is safe to re-run after any change to prep.py: `--replay` of an existing `trace.json`
  costs ~3 s and re-does every comparison, including the byte-identical-determinism check.
* Still no real data in macuda (plan rule 5): the only `.jtb` files this task made are in `/tmp/j15-*`, and
  `git status` in the worktree shows only `py/prep.py` and `py/trace_train_order.py`. `cuda-shim/`, `vendor/`,
