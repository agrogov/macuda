|---|---|

## Where the difference comes from (and why the per-row values move more than the means)

The per-row CE values are not what the gate compares, but they are worth recording because they explain the shape of the
means. For step 1 of the run, python vs C, per row:

```
py  1.1310  4.5112  0.1879  1.2306  4.4353  0.9190  0.7676  1.2721
c   1.1302  4.5154  0.1877  1.2299  4.4401  0.9190  0.7676  1.2737     max |d| 4.76e-03, mean |d| 1.56e-03
```

The largest per-row differences over the run are ~6.3e-03, on rows whose CE is ~4.5 (1.4e-3 relative), and they have
mixed signs, so the batch mean lands 1e-4–1e-3 away — the plan's choice of the mean, and design §10.3.2's 1e-3/1e-2
split, are calibrated for exactly this. The source is the model path, not a layout or an index: J30's dump-backward gate
pinned every layer's activations and all 300 LoRA gradients to ≤2.3e-05 against the CPU literal-loop reference, while
train.py runs *transformers'* installed attention/GDN kernels (sdpa + the hub GDN kernel) where jefftrain runs design
§3.6's literal recurrence — mathematically the same, different summation order, and CE is sensitive in long, near-one-hot
rows (up to 795 tokens here). Nothing here loosens a tolerance: the gate is the plan's, unchanged.

**Determinism**: re-running jefftrain over the same `.jtb` and adapter in exact mode produced a **bit-identical**
`steps.jsonl` (`cmp` clean), so a later card/shim run can be compared against this file without re-baselining. The Python
trace is reproducible too (the same run twice moved only in the last digits of some step means, e.g. step 8
1.242632 → 1.242653, and step 20's dev CE 0.77121 → 0.77117).

## Two diagnostics that shaped the script's defaults

Recorded because they are the reasons for choices other tasks may reuse, not part of the gate:

1. **TF32 would not hold the early gate.** The same 20 steps with the same `.jtb`/adapter but jefftrain's default
   compute mode (`EXACT=0`, no `JT_EXACT`) put step 5 at `1.31e-03 > 1e-3` (mean 0.492233 vs 0.492877) and failed that one
   step; steps 1–4 and 6–20 were inside their gates (worst later step 3.70e-03 at step 7). So `scripts/parity-steps.sh`
   defaults to exact and its trace is an exact-mode trace; `EXACT=0` reproduces the TF32 look. Both traces are kept:
   `steps.jsonl` (the gate) and `steps-tf32.jsonl` (+ `report-tf32.json`).
2. **The gate is the plan's 256-row, 20-step configuration.** A 64-row / 3-step plumbing smoke run (different schedule,
   worth 1/4 of the steps) landed at rel 2.15e-03 on step 3 — i.e. a much smaller row count, with a different lr
   schedule, is not the gated configuration and does not pass it. The gated run above is the one that matters, and its
   step 3 is 3.77e-04.
