# J47 — M8.1b: bf16 frozen weights behind JT_BF16_WEIGHTS

Plan M8 item 1 with design §6.1's alignment rules, on J46's cast kernel. The frozen text weights are kept in the
checkpoint's own bf16 in a second arena, their two GEMMs (`y = x W^T`, `dx = dy W`) run with bf16 operands and fp32
output, the activation operand is cast per call — and the fp32 copy of those weights is never allocated, so the memory
really drops. Unset (or `=0`) is the fp32 path byte for byte; exact mode ignores the toggle and says so.

## 0. The checkpoint's stored dtype (asked for first)

```
$ ssh gpubox 'python3 - <<PY  (reading the safetensors headers only, no GPU)'
model.safetensors: 473 tensors, dtypes {'BF16': 473}
  language_model.layers.0.input_layernorm.weight        BF16 [1024]
  language_model.layers.0.mlp.gate_proj.weight          BF16 [3584, 1024]
  language_model.layers.23.mlp.down_proj.weight         BF16 [1024, 3584]
  language_model.layers.3.self_attn.q_proj.weight       BF16 [4096, 1024]
  language_model.layers.0.linear_attn.in_proj_a.weight  BF16 [16, 1024]
  language_model.layers.0.linear_attn.conv1d.weight     BF16 [6144, 1, 4]
readout.safetensors: weight BF16 [255, 1024]
```

**Every one of the 473 tensors is BF16 on disk**, so keeping a frozen weight as bf16 loses nothing at all: `Wb` holds
the checkpoint's exact bits and the load is a `cudaMemcpy` (no staging buffer, no widening kernel). The only new
rounding in the bf16 mode is the bf16 cast of the *activations* (`jt_f32_to_bf16_n`) that the GEMM needs, 8-bit
mantissa instead of TF32's 10. The measured 1.99 GB fp32 arena is the 497,614,848 linear elements exactly
(`497614848 x 4 B = 1.99 GB`); those become 0.995 GB, and the fp32 arena keeps the 498,784 non-linear floats (norms,
conv taps, gate vectors) = 2.0 MB, so the load prints `weights: bf16 (1.00 GB)`.

## 1. What landed (7 files, all mine)

| file | what |
|---|---|
| `src/gemm.h`, `src/gemm.c` | `gemm_bf16_ok()` — design §6.1's alignment rule in this wrapper's terms (each operand's leading dimension, i.e. its row length and contiguous extent, a multiple of 8 elements; both bases 16-byte aligned) — and `gemm_bf16()`, `cublasGemmEx` with `CUDA_R_16BF` A and B, `CUDA_R_32F` C, `CUBLAS_COMPUTE_32F`. Both mirror `gemm()`'s argument mapping; a shape that fails the rule is refused with its numbers, not silently run on another kernel |
| `src/linear.h` | `const unsigned short *Wb` next to `W`, plus the contract: `Wb != NULL` means the bf16 storage; `W` is then the shared 8-word marker (below), never a weight |
| `src/linear.c` | one `weight_gemm()` used by both weight GEMMs: bf16 path = cast the activation into the arena's work half (16-byte aligned inside it) and `gemm_bf16`; fallback when the rule does not hold = widen the weight with `jt_bf16_to_f32_n` and take today's `gemm()`. `lin->Wb == NULL` is today's call, argument for argument |
| `src/model.h`, `src/model.c` | `Model.wb`/`wb_el` (the bf16 arena), `Model.w_mark`, `put_bf16()`/`reserve_bf16()` (slots rounded to 8 elements so every operand base is 16-byte aligned), the `JT_BF16_WEIGHTS` switch, and the `weights: bf16 (x GB)` / `weights: bf16 ignored (...)` startup lines |
| `test/test_gemm.c` | `check_bf16()` (CPU reference on bf16-rounded inputs, via `test/harness.h`'s `jt_f32_to_bf16`) and `check_bf16_ok()` (the rule, 9 cases) — 112 -> 129 checks |

Two implementation notes worth carrying:

* **The marker.** `src/layer_mlp.c`'s argument check tests `lw->gate.W == NULL` ("an MLP linear has no frozen weight"),
  and that file is not mine. So a bf16 linear still has a non-NULL `W`: it points at `Model.w_mark`, eight zeroed fp32
  words at the end of the fp32 arena, shared by every bf16 linear and never dereferenced as a weight (documented in both
  headers). The alternative — `W = NULL` — needs a one-line change in `src/layer_mlp.c:146/166` (its two `W == NULL`
  guards should also accept `Wb != NULL`); that file belongs to another task, so this card did not touch it.
* **The staging buffer.** With the linears in the bf16 arena no *model* tensor needs the bf16 staging buffer any more,
  so it is now sized `max(largest model tensor, the readout's 255 x 1024)`. The first toggle run died on exactly that
  (`model: the readout has 261120 elements, more than the 24576-element staging buffer`) — the one bug this card had,
  found by running the trainer rather than by reading it.

it is the property `G-m8probe` exists to judge; the mode is off by default and cannot touch the default or exact paths.
