# J38 — M8.3 (optional): fused kernels

Plan M8 item 3, word for word: "**Fused kernels**: rmsnorm + the following linear's input cast; silu_mul into the
down_proj prologue; the attention softmax fused with the scores (flash-style) for L > 512." The M8 chain was started
(J37 PASS), so this card is live.

The short version: **the two "cast/prologue" fusions are predicated on M8.1**, and M8.1 did not land (J36 BLOCKED — no
`jt_f32_to_bf16_n`, no bf16 weight pointer, no bf16 GEMM, so in v1's fp32 path there is no input cast and no GEMM
prologue to fuse anything into: `src/linear.c:61` hands cuBLAS the fp32 pointer and nothing else happens between the
norm and the GEMM). **The third piece is implementable in `kernels/attn.cu` + `src/layer_attn.c`, but not legally**:
plan rule 2 requires `ref/attn.c`'s reference and a `test/k_attn.c` group before a new kernel exists, and both are
other tasks' files. So I spent this card measuring what each piece is worth, on gpubox, at the real training shape, so
the decision can be made with numbers instead of guesses. That measurement also found that the **biggest cost in the
attention path is not the softmax at all** — it is `kernels/misc.cu`'s head-major transposes, which are launched with
only **8 blocks** for the whole GPU and cost **7.4 % of a TF32 step (15.8 % exact)** on their own. That is a one-file,
one-function fix in a file (misc.cu) this task does not own, and it is worth more than all three M8.3 pieces together.

**No tree change survives**: `git diff` is empty, sources are `git checkout`ed, and the only new files are this note and
`notes/J38.wip.patch` (the temporary `JT_PROF` instrumentation and the four ablation probes, kept so a follow-up can
re-measure in one sync — it is measurement scaffolding, not a proposal).

## 1. What blocks each piece, and what it would be worth

| plan M8.3 piece | blocked by | measured worth on this workload |
|---|---|---|
| rmsnorm + the following linear's input cast | M8.1 (J36): no `jt_f32_to_bf16_n`, no bf16 GEMM, no `Linear.Wb`; the fusion target does not exist in the fp32 path | ≤ **0.1 %** of a step (the norms themselves are 0.0154 ms/call, 0.74 ms/step; the cast it would absorb is ~25 MB per norm) |
| silu_mul into the down_proj prologue | same (the "prologue" is the bf16 cast of the GEMM operand) | **~0.3 %**: `k_silu_mul_fwd` is 0.195 ms/call → 9.4 ms/step (0.9 %), and a cast-fused version still reads h1/h2 and writes 3584/token, saving under half of that |
| attention softmax fused with the scores (flash-style, L > 512) | plan rule 2: a new kernel needs `ref/attn.c` + `test/k_attn.c` (J09's files, not mine); `layer_attn.c` alone cannot express it | ceiling = the **whole per-row attention block: 10.1 % of a TF32 step, 17.1 % exact** — of which the softmax kernels are 0–8 % and `misc.cu`'s transposes 7.4–15.8 % (tables in §3) |

The row lengths say the plan's `L > 512` condition is half-true at this data (`prep.py`'s 256-row train sample:
min 324, max 795, **mean 520**, mean max-L per batch **527**, **47 % of rows > 512**, mean Σ L² per batch 2.22e6) — but
the per-row costs that dominate (transposes, launches) do not depend on L, so a `L > 512` gate on a fused kernel would
forgo most of the win at this distribution anyway.

### 2.3 Ablations: the wall-clock price of the per-row attention (2 reps each, mean of steps 5–20)

Same 20-step runs, EXACT and TF32 (no `JT_EXACT`), probes from `notes/J38.wip.patch`. Reproductibility across reps is
±0.3 %, so a 1 % effect is real.

| probe | exact s/step | Δ | TF32 s/step | Δ |
|---|---:|---:|---:|---:|
| baseline | **1.141 / 1.140** | — | **1.044 / 1.042** | — |
| `JT_NOATTN=1` — the whole per-row loop skipped (fwd and bwd) | 0.945 / 0.946 | **−0.195 = 17.1 %** | 0.943 / 0.934 | **−0.104 = 10.1 %** |
| `JT_NOTR=1` — only the 5 head-major transposes/row skipped | 0.958 / 0.961 | **−0.180 = 15.8 %** | 0.964 / 0.966 | **−0.078 = 7.4 %** |
| `JT_NOSMZ=1` — softmax replaced by a memset of P (no stale data) | 1.048 / 1.047 | **−0.093 = 8.2 %** | 1.047 / 1.046 | −0.004 ≈ 0 |
| `JT_NOSM=1` — softmax simply skipped (P left stale) | 1.045 / 1.047 | −0.095 | 1.047 / 1.042 | −0.002 |

Two honest caveats about that table:

* The four probes **do not add up** (transposes + softmax + GEMMs > the row loop), because each removal lets another
  piece absorb the slack; treat `JT_NOATTN` as the only clean number (the ceiling) and the rest as upper bounds.
* The softmax's two answers disagree by ~10×: the ablation says removing it gives back 8.2 % of an exact-mode step, the
  events in §2.2 say the kernel itself is ~0.6 % (0.047 + 0.041 ms per row-visit ≈ 8 ms/step). I re-ran the softmax
  ablation with P zeroed rather than stale (to rule out a denormal/stale-data artefact in the following GEMMs) and the
  delta did not move, so the 8.2 % is reproducible but is not all kernel time — it is what the step gets back when that
  launch chain disappears. Whichever reading is right, the softmax alone is a rounding error next to the transposes.

## 3. What the follow-up should actually do (in pay order)

1. **Fix `kernels/misc.cu`'s head-major transposes first — 7.4 % (TF32) / 15.8 % (exact) of a step, one function.**
   `jt_to_head_major` / `jt_from_head_major` launch `jt_grid_rows(heads)` blocks (`misc.cu:230`, `:236`), i.e. **8 blocks
   — one per head — for the whole GPU**, and each block walks `rows × 256` floats with a 256-thread block. That is ≈90 GB/s
   effective (0.41 ms for the ≈37 MB the fwd's five prep passes move for one 520-token row), ~18× off this card's
   bandwidth. One block per
   (head, token-tile) — or a flat grid-stride over the `rows × 256` elements — is the fix, and it needs no new op, so it
   needs no new reference: `test/k_misc.c`'s existing group already gates it. **This is worth more than M8.3 items 1–3
   combined and it is not in this task's file list.** Same for `jt_kv_expand`/`jt_kv_reduce` (they are `grid_rows(rows)`,
   so they are fine, but they are 2 of the 5 preps that touch the same data twice).
2. **Then** decide on the flash-style fused kernel. Its ceiling is the 10.1 % (TF32) / 17.1 % (exact) row loop, and it is
   only worth cutting if it **subsumes the transposes** (it can: read token-major q/k/v with a 2048-stride, write o
   token-major) and the QK/PV GEMMs. At 2.25 GFLOP of QK+PV per mixer call and the shapes above, an fp32 CUDA-core
   kernel with proper register tiling is the only option (the shim's tinycc build has no WMMA path and TF32 is not a
   mode any kernel uses), so its arithmetic is not free — but there is ~100 ms/step of transposes and launch slack to
   win. It needs `ref/attn.c` (`ref_attn_flash_fwd`) and a `test/k_attn.c` group before the kernel may exist (plan
   rule 2), plus its adjoint if the backward is fused too; cut it as its own task with those files in its list.
3. **Skip M8.3 items 1 and 2 until M8.1 lands**, and then do them for the memory, not the speed: their measured total is
   under 1 % of a step, while M8.1's own win was measured at ~4 % (J36, blocked). If J36 is re-cut, its cast kernel
   (`jt_f32_to_bf16_n` in `kernels/misc.*`) is the natural place for both fusions: `rmsnorm_fwd` gaining a bf16 output
   (`kernels/norm.cu` + `norm.h` are mine) and `k_silu_mul_fwd` gaining the down_proj's bf16 operand (`act.cu`/`act.h`),
   each needing the reference's second output in `ref/norm.c` / `ref/act.c` first (also not mine).
4. If someone wants a cheap in-file win from this card's list and does not want to wait: `attn_softmax_fwd` is 0.047 ms
   per 8-head 520-token row against ~13 MB of traffic (≈280 GB/s), with three passes over S and two `expf`s per element,
   and its block reductions are the naive `__syncthreads` tree (`kernels/attn.cu`, `attn_block_max/_sum`, 8 levels ×
   2 barriers, run 3× per row). A one-online-pass rewrite with warp-shuffle reductions is contained in
   `kernels/attn.cu`+`attn.h` (my files) and is gated by the existing `test/k_attn.c` group, but its prize is the
   **exact mode only** (8.2 % upper bound above, ~0.6 % if the events are right, ~0 % in TF32 where the step is
   launch-bound). I did not land it: it is not plan item 3, it moves no TF32 number, and it would have muddied the
   "M8.3 is blocked" signal this note exists to send.
