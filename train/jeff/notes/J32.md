## What the script does

It only orchestrates, on gpubox, inside `~/CLM-8B` — the real data, the `test.jtb` and the predictions stay there
(plan rule 5); nothing is written into macuda, and no row content is printed or stored (`compare_preds.py` itself
prints only aggregates).

1. `scripts/gpubox-build.sh` (sync + `make nv ARCH=sm_120`) unless `JT_SKIP_BUILD=1`, so the numbers belong to the
   tree it was called from. **The binary tree is `JT_REMOTE`, exactly like the other gpubox scripts**:
   `~/$JT_REMOTE/build/nv/jefftrain`, and `py/prep.py` from the same tree; the parallel-task isolation is therefore
   `export JT_REMOTE=macuda-train/wt-J32`.
2. On the box: `cd ~/CLM-8B`, `. tools/jeff_lora/cuda/env.sh` (`DATA`, `VENV`, `REMOTE_MODEL`, the HF/tokenizer env).
3. Temperature from the checkpoint itself, not hard-coded: `load_decision_config(<model>)["temperature"]`
   (train.py's `--eval-temperature checkpoint` path, the reference run's own value `1.0121076495126538`).
4. `$VENV/bin/python ~/$JT_REMOTE/py/prep.py --clm ~/CLM-8B --model ~/models/jeff-base
   --eval test=$DATA/test.jsonl --batch 4 --out-dir <run dir>` → `test.jtb`.
5. For `mode` in `tf32 exact`: `jefftrain --model ~/models/jeff-base --eval-only --eval test=<run>/test.jtb --batch 4
   --eval-temperature <T> --output <run>/<mode>`, once plain and once with `JT_EXACT=1` (one nv build serves both modes,
   the same convention as `scripts/card-check.sh`). The script greps the run's own `gemm:` line and fails if it is not
   the expected mode, so a stale env can't quietly compare TF32 twice.
6. `$VENV/bin/python tools/jeff_lora/cuda/compare_preds.py <run>/<mode>/pred-test.jsonl <ref> --max-dp 0.05
   --min-agree 158`. `<ref>` is the newest `data/ovril_detect/runs/cuda-parity-fp32-*/pred-test.jsonl` (override with
   `JT_REF_PREDS`); the script is CLM-8B's, not a copy.
7. One verdict line, `parity-eval: PASS|FAIL`, and the ssh exit code is the script's exit code (non-zero on any gate
   failure, a missing binary/prep/reference, or a mode that does not match).

`--batch 4` is required, not decoration: it is the flag prep.py wrote `test.jtb` with, and it makes the eval batch
`max(2, 4*2) = 8` rows, which is what the sidecar (`eval_batch`) and the file's 20 batches hold, so jefftrain's
flag/`.jtb` check passes.

## Notes for later tasks

* **M7.2** (eval parity on the card) reuses these numbers: gpubox's `…/jefftrain-parity-<TS>/{tf32,exact}/pred-test.jsonl`
  is the reference for the shim run, and D§10.4's card gate is `max |dp| < 0.01` against gpubox jefftrain — not
  against the PyTorch port, which M6.1 has now cleared at 0.0015.
* The script is safe to re-run any time a kernel or the model changes: it syncs+builds first by default, writes a new
  timestamped run dir, and never overwrites an earlier result.
* Knobs are documented at the top of the script: `JT_REMOTE` (binary tree — always set it when other tasks run),
  `JT_SKIP_BUILD`, `JT_PARITY_TS` (run-dir suffix), `JT_REF_PREDS`, `JT_MAX_DP`, `JT_MIN_AGREE`. The last two default
  to the plan's 0.05/158 and must not be loosened; they exist so the gate can be *tightened* or spot-checked.
* The `gemm:` mode line is asserted per run, so TF32 and exact cannot be silently swapped by a leftover `JT_EXACT`.
* No `--init-adapter`: M6.1 is the base checkpoint's eval, which is what `cuda-parity-fp32-*` also was
  (`"init_adapter": null, "eval_only": true` in its `report.json`).
