## The change (two files)

### `src/linear.c`: only the backward stub replaced

```c
e   = s * (dy B)              gemm(0,0)  n x rank x out   alpha s, beta 0     once, reused (D§4.2's own optimisation)
dx  = dy W                    gemm(0,0)  n x in   x out   beta = accumulate_dx ? 1 : 0
dx += e A                     gemm(0,0)  n x in   x rank  beta 1              (only when lora)
dB += s * dy^T u              gemm(1,0)  out x rank x n   alpha s, beta 1     into lora->grad + b_off
dA += e^T x                   gemm(1,0)  rank x in x n    beta 1              into lora->grad + a_off
```

i.e. D§4.2's four lines as D§5's table lists them, in ref/linear.c's order (`e` first, then dx, then the two parameter
gradients). Both dx GEMMs take `beta = 1` when `accumulate_dx` is set, which is what design §4.6 needs: a residual
gradient buffer may already hold another path's contribution, and `linear_bwd` must add to it, never overwrite it.
The frozen linear (`lora == 0`, the GDN `in_proj_a`/`in_proj_b`) runs the first GEMM only and writes no parameter
gradient, as src/linear.h says.

Decisions worth naming:

* **`e` comes from the arena's work half** (`jt_work_alloc`, `n * rank` floats — 592 at this test's shape, 67 K at
  N = 4200) and is given back with `jt_work_restore` before returning: a backward may not `cudaMalloc` (design §6.2), and
  a caller must be able to call it once per layer per step without the arena creeping.
* **The offsets check moved into one helper** (`lora_offsets_ok`) and now runs in the forward before the `n == 0` early
  return as well — a wrong `a_off`/`b_off` is a broken `Linear` and should be named whatever `n` is. That is a small
  behaviour change in `linear_fwd` (n == 0 with bad offsets now returns `JT_LAYER_FAIL` instead of `JT_LAYER_OK`); no
  caller in the tree passes a bad one, and the compiler's `-Wall -Wextra` is still clean.
* **The argument checks** are the forward's plus three that only the backward can break: `dy == NULL`,
  `dx == dy` (dy is read by three of the five GEMMs, so writing dx over it would read a half-updated buffer — the same
  rule as the forward's `y != x`), and `u == NULL` on a LoRA linear (two of the GEMMs take it). A frozen linear with
  `dx == NULL` is `JT_LAYER_OK` with no work: there is nothing to compute at all. All of them print
  `linear: linear_bwd: <why> (<stem>)` and return `JT_LAYER_FAIL`. The `not_implemented()` helper is gone with the stub.
* **`MT_LORA_SCALE` is the `s` of both scaled GEMMs** (`dB`'s alpha and `e`'s alpha) and is not applied twice: `e` carries
  `s`, so `dx += e A` and `dA += e^T x` are unscaled (D§4.2's "write `e = s (dy B)` once and reuse it").

### `test/test_linear.c`: the new GPU gate for it

Two runs, because the plan asks for two different things:

| run | what it proves |
|---|---|
| `--fd` | the plan's "GPU finite-difference check on a [37, 64] → [48] linear in exact mode": dx, dA and dB against a central difference of `L(x,A,B) = <dy, y>`, **every** element of x (2,368), of A (1,024) and of B (768), one at a time, h = 1e-2, L summed in double on the host. A frozen `[37,64] → [48]` case checks the `dy W`-only path, and three extra checks cover `accumulate_dx`, `dx == NULL`, and the bad-call contract. |
| `--model/--adapter/--ref [--layer i]` | the plan's second half: `grad.{stem}.lora_A/B` of layer 23's MLP against `ref.safetensors`, i.e. the same three linears with the checkpoint's own W, x and dy. |

Four things about the test that decide whether the numbers mean anything:

* **The FD has no truncation error, so `h` can be large.** y is affine in x and multi-affine through `x A^T B^T`, so
  `L` is exactly linear in each single element and the central difference is exact at any `h`; what is left is the
  forward's own fp32 rounding, which `h = 1e-2` pushes three orders below the gate. Only synthetic data (plan rule 5),
  from `harness.h`'s xorshift32 seeds: x ~ U(-1,1), W and A ~ U(-1/sqrt(in), +), B ~ U(-0.1,0.1) — `py/make_adapter.py`'s
  distributions, so the LoRA path is a small correction to W's, as in the model.
* **The MLP is walked by hand, not through `layer_mlp_bwd`.** Layer 23 is a full-attention layer, so the gradient
  entering its MLP is `grad.layer.23.out` (design §4.6), and the three parameter gradients are three `linear_bwd` calls
  around design §4.5's elementwise chain. The test therefore calls `rmsnorm_fwd`, three `linear_fwd` (keeping the u's),
  `k_silu_mul_fwd`, then `linear_bwd` down/gate/up and `k_silu_mul_bwd` with **its own buffers** — no arena save, so plan
  M5.1 item 3's `layer_mlp_fwd` save layout is not on this gate's dependency path. `--layer 0` (a GDN layer) works too,
  and is the more interesting one: see "the two shapes of grad.layer.i.out" below.
* **The adapter key comes from the flat buffer's table, not from `Linear.stem` — see the finding below.** The key is
  `LoraEntry.stem` at the entry whose `off`/`b_off` are the Linear's `a_off`/`b_off` (src/lora.h), which is what
  `lora_load_adapter` keyed on, so the comparison is against the same 300 tensors train.py wrote.
* **Exact mode is required, not assumed**: `gemm_init()` prints the mode and the program exits **2** if it is TF32
  (`JT_EXACT=1` is design §5/§11.1's knob). A TF32 backward moves by ~1e-3 of its own scale, which is the gate itself.

The gate was **watched failing**, twice, on real bugs in the test (both fixed before the numbers above):

1. the first version took the analytic gradients before anything had uploaded `x`/`param` and before a forward had filled
   `u` (the FD loop is what uploads them). Output: `FAIL dx rel=0.469`, `FAIL dA rel=1`, `FAIL dB rel=1`,

   the **frozen** case, whose `dy W` touches neither `x` nor A/B. That is exactly the signature the gate should give.
2. then `dB` alone failed at **rel=1.54** while dx and dA passed: `dB`'s numeric side was perturbing `hparam[i]` instead
   of `hparam[b_off + i]`, i.e. A's words instead of B's. So a dB-specific error is invisible to the dx and dA gates and
   this one catches it at O(1).

Neither number is a tolerance change: the gate is the plan's own gradient gate (M5.1's `--grad-rel 5e-3`).

#### The two shapes of `grad.layer.i.out`, and why layer 0 is worth running too

`grad.layer.23.out` is nonzero at **only 2 of 107 tokens** (the `dL/dm` line: 107,520 of 109,568 values are exactly

## A finding in someone else's file: `Linear.stem` dangles after `model_load`

`src/model.c` builds every `Linear.stem` in a heap pool and then frees it at the end of `model_load`
(`free(L.pool)`, src/model.c:301), so every `stem` it handed out is a pointer into freed memory. The first version of the
layer-23 run showed it directly:

```
st: .../ref.safetensors: st_get: no tensor named "grad..lora_A"     <- the stem came back as ""
```

Two consequences: any message that names a linear (`src/linear.c`'s `bad_args`, `src/layer_mlp.c`'s) prints `?` or
garbage, and any code that keys on `Linear.stem` (design §9.2) reads freed memory. **Not fixed here — `src/model.c` is
not this task's file.** The change it needs is one line: keep the pool alive (put it in the `Model`, or store the stems
as a static/`const char *` table built from `src/model_table.h`, which already holds the names). This test does not
depend on it: it takes the adapter key from `LoraEntry.stem` (src/lora.c's own copy, the one `lora_load_adapter` and
`lora_save_adapter` key on), matched to the Linear by `a_off`/`b_off`.

## Numbers worth recording for the later tasks

* **The backward is 5 GEMMs**: at the plan's batch (N = 4200) a 1024 → 3584 projection's backward is
  `e` 4200x16x3584x2 = 0.48 GFLOP, `dx = dy W` 4200x1024x3584x2 = 30.8 GFLOP, `dx += e A` 4200x1024x16x2 = 0.14 GFLOP,
  `dB` 3584x16x4200x2 = 0.48 GFLOP, `dA` 16x1024x4200x2 = 0.14 GFLOP — i.e. **about 32 GFLOP against the forward's 31**,
  so a training step is ~2x the forward's dense math, as design §15 assumes. The rank-16 pairs are 1.2 GFLOP, 4% of it.
* **`e` is the only work temporary**: `n * rank` floats (268,800 B at N = 4200), taken from the arena's work half and
  given back, so `layer_bwd`'s loop does not grow the arena.
* **The gradients are accumulated, never written**: `dA`/`dB` land in `ctx->lora->grad + a_off / b_off`, and a forward's
  `u` is an input of both. So M5.2's step must `lora_zero_grad` once per accumulation group (as the plan says) and must
  not free or move the flat buffer between the forward and the backward.
* **For M5.1 item 3 (`layer_mlp_bwd`): the numbers it must reproduce are in this note.** Its `dm` on entry is
  `grad.layer.{i}.out`, its dA/dB must equal the ones above for the same layer and adapter at this fixture
  (`--layer 23` and `--layer 0`), and `dL/dm = d(gate) + d(up)` must be finite and dense for layer 0. Its
  `k_silu_mul_bwd` + `linear_bwd(down/gate/up)` order is design §4.5's; the test's hand-rolled version is the reference
  for it.
* **For M5.4 (the card checkpoint)**: `test_linear --fd` and `--model … --ref … ‑‑layer 23` are the two lines to run
  with `JT_EXACT=1 TINYCUBLAS_TC=0`; the numbers above are the gates they should print. The `--fd` run is 1.4 s on the
  card's class of GPU and needs no checkpoint at all (it allocates a zeroed `Model` for `jt_ctx_alloc` and never touches
  it), so it is a cheap first card check of the shim's `cublasGemmEx` with `ta=1` — the first layer-level user in the tree of
  gemm's transposed-argument path (test_gemm covers all four `(ta,tb)` combinations, but no layer needed `ta=1` before
  the backward's `dy^T u` and `e^T x`).
* **The FD gate's tolerance is the plan's 5e-3, and there is room to spare** (2e-05 measured): if a later change makes it
  ten times worse, that is a real regression and not noise.
