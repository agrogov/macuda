## The frozen interface (what the four parallel layer tasks code against)

Design §13's struct is used verbatim; the only addition is a return code, because a stub has to say "not implemented"
without aborting a test run.

```c
struct Linear { const float *W; int in, out; int lora; size_t a_off, b_off; const char *stem; };
int linear_fwd(JtCtx *ctx, const Linear *lin, const float *x, int n, float *y, float *u_save);
int linear_bwd(JtCtx *ctx, const Linear *lin, const float *x, const float *u, const float *dy, int n, float *dx,
               int accumulate_dx);

int layer_mlp_fwd(JtCtx *c, const LayerWeights *lw, const float *x_in, int n, const JtBatch *b, float *x_out, int mode);
int layer_mlp_bwd(JtCtx *c, const LayerWeights *lw, const float *x_in, float *dres, int n, const JtBatch *b);
int layer_gdn_mixer_fwd(...);   int layer_gdn_mixer_bwd(...);      // same shape as the MLP pair
int layer_attn_mixer_fwd(...);  int layer_attn_mixer_bwd(...);
int head_fwd(JtCtx *c, const float *x, int n, const JtBatch *b, const HeadBatch *hb, float *final, float *logits,
             float *loss, int mode);
int head_bwd(JtCtx *c, const float *x, int n, const JtBatch *b, float *dres);

// model.c: the layer's two halves in order (mixer then MLP), and the whole forward
int layer_fwd(JtCtx *c, int i, const float *x_in, int n, const JtBatch *b, float *x_out, float *post_mixer, int mode);
int layer_bwd(JtCtx *c, int i, const float *x_in, const float *post_mixer, float *dres, int n, const JtBatch *b);
int model_forward(JtCtx *ctx, const int *ids, int n, const JtBatch *b, float *saved_in, float *post_mixer);
```

The split point is the one `dump_ref.py` writes (design §10.2): a **mixer** is `layer.{i}.in -> layer.{i}.post_mixer`
(input norm + mixer + residual) and the **MLP** is `layer.{i}.post_mixer -> layer.{i}.out` (post-attention norm + MLP +
residual), so `test_layer`'s three parts are exactly those keys. `model_forward` keeps the 25 saved layer inputs of
design §6.2 (`saved_in[i]` is layer i's input, `saved_in[24]` is layer 23's output, which `head_fwd` takes), does them with
zero copies by writing each layer's output into the next slot, and is always a forward-only sweep — the backward re-runs
each layer in `JT_FWD_SAVE` mode (`layer_fwd` then `layer_bwd`), which is design §6.2's layer recompute.

Decisions a later task must know (each is in the header at the point it matters):

* **`x_out` may alias `x_in`.** A fwd writes `x_out = x_in + <its path>` and never reads `x_out`; if it aliases `x_in`
  the function must have finished reading `x_in` before it accumulates (the input norm is computed first, so the natural
  order already satisfies this). `layer_fwd` uses the alias to run a layer without an extra copy.
* **`dres` is in+out.** On entry `dL/d(x_out)`, on return `dL/d(x_in)`, with this path's contribution added — design
  §4.6's "accumulate into the residual gradient buffer; never overwrite it". `head_bwd` is the exception: it starts the
  sweep and writes `dres` in full.
* **Modes.** `JT_FWD_SAVE` = keep what the bwd reads in the arena's *save* half; `JT_FWD_ONLY` = keep nothing, use *work*
  temporaries only. `layer_fwd` calls `jt_saves_reset()` itself before a SAVE pass; a direct call to one piece (what
  `test_layer` does) must call it first. In SAVE mode `layer_fwd` **requires** `post_mixer` (non-NULL, not the same buffer
  as `x_out`) because the MLP's fwd overwrites its own input and `layer_bwd` takes the post-mixer residual as an argument.
* **The arena is two halves.** `jt_save_alloc` from the front, `jt_work_alloc` from the back, `jt_work_mark` /
  `jt_work_restore` around a bwd's temporaries. No `cudaMalloc` inside a layer call (design §6.2); overflow dies with the
  numbers and names `JT_ARENA_FLOATS_PER_TOKEN` (98304 floats/token = design §6.2's "about 40 K" forward + backward,
  plus `2 x 8 x lmax^2` floats for one row's P and dP).
* **The stream is non-blocking, and that bit me.** `ctx->stream` is `cudaStreamCreateWithFlags(..., cudaStreamNonBlocking)`
  (design §12 forbids `cudaStreamCreate`), and this driver does **not** order the legacy null stream against it: a
  `cudaMemcpy` on the null stream and a kernel on `ctx->stream` may run in either order. Symptom seen on gpubox while
  testing: a weight arena that read back as zeros. Two consequences, both now in the code: `jt_ctx_alloc` ends with one
  device-wide barrier, which orders everything a load did before the context existed (`model_load`,
  `lora_load_adapter`, `jt_batch_set`); and anything uploaded or read back *after* that must use `ctx->stream` (as
  `test_layer`'s `ref_upload` and its comparison readback do). A layer body should keep every launch and copy on
  `ctx->stream` and let the caller synchronise.
* **`Linear.stem`** is the adapter key prefix (the tensor name minus `.weight`, the same string as `LoraEntry.stem`), not
  the full tensor name. The two frozen GDN projections are `Linear`s with `lora == 0`: `src/model_table.h` keeps only
  their names (J12 stores them as `const char *`), so `model.c` states their `[16,1024]` shape from `MT_GDN_HEADS` /
  `MT_HIDDEN` and `st_get` checks it. `linear_bwd` with `lora == 0` therefore has to compute `dx = dy W` and nothing else.
* **The head.** `head_fwd` now takes a `final` output (`[n][1024]`, dump_ref's `final` key; may be NULL) as well as
  `logits` (`[B][n_opts]`). `loss` is a **host** scalar and is the one place that synchronises (train.py's
  `(per * wt).sum() / gw`, i.e. the sum of `ce_head`'s per-row losses); pass NULL to stay asynchronous. `HeadBatch.targets`
  and `.wrow` may be NULL = "logits only" (no loss, no dlogits) — that is `test_layer --head` without a fixture.
* **`test_layer`'s extra `--jtb`.** `ref.safetensors` has the logits and the loss but **not** the targets they were
  computed from, so the loss can only be re-derived from the fixture the dump used. `--jtb` is optional: without it the
  head compares `final` and `logits` and prints `loss skipped (no --jtb: the reference has no targets)`. With it, the
  fixture's rows, lengths, packed ids and per-row live counts are checked against the reference before anything runs, and
  `gw` is the batch's weight sum (1 + 1 = 2 for the shared fixture). The layer parts do not need `--jtb`.
* **`model_backward` is deliberately not declared here.** It is plan M5.1's driver; declaring it now would freeze a
  signature written without the backward tests in front of me. `layer_bwd`, `layer_fwd(SAVE)`, `head_bwd` and the arena
  are what it needs, and adding the declaration when it is written disturbs none of the five files.
